# 方形游戏画面 + UI 分离：可行性账

> 目标源自人的设计：**世界渲染区严格 1:1**（地板/墙/角色/光照/迷雾/雨雪），
> **UI（对话框、暂停菜单等）不在这个世界区里**。UP 主录视频时捕获纯净方形画面，
> 自己把 UI、摄像头、字幕拼到别处；方形素材同时兼容竖屏与横屏成品。
> Rust 版同源提案在 `rust-bevy-endless-corridor/docs/dual-window-rendering.md`（未实现）。

## 1. 现状（实测，别按想象算）

- 渲染库是**单窗口**架构：`初始化窗口 / 初始化窗口隐藏 / 设窗口尺寸 / 设窗口无边框`，
  **没有**第二窗口、窗口位置、置顶、焦点切换、渲染纹理（离屏画到纹理再贴）这些入口。
  所以"前面方形窗 + 后面 UI 窗"不是一个开关，是桥接层要加的原生能力。
- 图块原型当前窗口 **800×600**。地图世界宽度实测：
  01 是 16 格×48 = 768；02 是 10×48 = 480；**03 是 18×48 = 864**。
  也就是说 03 现在左右各被裁掉 32px（`场偏横 = (800-864)/2 = -32`）。
  世界区要方形且不裁图，边长至少 **864**（取整 896 或 900 更稳）。
- 600×600 的方形要装下 18 格，得把 `格边` 压到 33（600/18），图块会变小一圈；
  900×900 则保持 48 的格边，只多留边。

### 1.1 绿键（红绿灯里的放大键）灰掉：已实测，运行时能点亮

- 现象：窗口左上角三个按钮里，绿色那个是灰的，点不了、进不了全屏。
- 根因：raylib 创建窗口时默认 `FLAG_WINDOW_RESIZABLE` 没开（GLFW 窗口不可调整），
  macOS 就把 zoom/全屏键置灰。原型从来没调过 `设窗口可调整`，所以一直是灰的。
- 实测对比（同一份代码，只差一行 `R.设窗口可调整(真)`）：
  不调 → 绿键灰；调了 → **绿键变亮，可用**。桥接里 macOS 走
  `SetWindowState(FLAG_WINDOW_RESIZABLE)`（`渲染桥.c` 的 `XT_SetWindowResizable`），
  运行时切换有效，不用改桥接、也不需要在创建时就传参。
- **但点亮不等于能用**：本引擎布局全按 `窗宽=800 / 窗高=600` 常量算（`场偏横/场偏纵`、
  存档表 `表左/表宽`、菜单坐标），`像素比` 也是启动时算一次。窗口一被拖动/最大化，
  画面会错位、字体图集也可能糊。所以顺序是：**先做第 2、3 节的"分层 + 按窗口尺寸自适应布局"，
  再开 `设窗口可调整(真)`**；在那之前保持绿键灰着，比开了却错版强。

## 2. 渲染库要支持的两种模式（上游能力诉求）

这一节写的是**给渲染库上游的诉求**，不是现在就能用的能力。目标：同一套游戏代码，
能在"UI 在游戏窗口里"和"UI 在游戏窗口外"两种渲染模式之间选。

### 模式一：UI 在游戏窗口内渲染（窗口自适应）

- UI（对话框、暂停菜单、存档界面、开屏提示）与方形世界区画在**同一个窗口**里，
  UI 排在方形区之外（右侧竖条或底部横条），窗口多大、UI 带就跟着多大。
- 窗口尺寸要能自己适应：800×600、1280×720、4:3、16:9、最大化、全屏都算合法尺寸。
  **世界区永远是正方形**——取 `min(可用宽, 可用高)`，再向下取整到格边的整数倍，
  剩下的像素才归 UI 带。窗口变形时世界区不变形、只换留边位置。
- 这条路径对录视频的 UP 主的意义：窗口本身就是"方形画面 + UI 在一起"的标准产出，
  不想裁就直接用；想裁就切下面的模式二或纯画面模式。

### 模式二：UI 在游戏窗口外渲染

- 游戏窗口只画方形世界（干净到可以直接捕获），UI 在**另一个窗口**里画：
  可以摆在游戏窗后面/侧面，甚至放到第二块屏。
- 这就是"Mac 上前面 800×800 方形窗 + 后面 UI 窗"的正解，键盘由游戏窗独占，
  ESC 时把按键语义切到 UI 那套界面（单进程内就是状态机，不需要跨进程转发）。

### 上游还缺什么（按优先级）

1. **创建时就能声明可调整**：现在只有运行时的 `设窗口可调整`，创建时没有选项；
   想要"一开窗就是自适应"的窗口，得在 `初始化窗口` 上带一个选项（如 `选项{可调整:真, 全屏:假}`）。
2. **尺寸变化的通知/查询**：`取屏幕宽/取屏幕高` 已有，但缺"窗口被拖大/最大化/进全屏了"
   这类事件；现阶段只能每帧轮询比较宽高，写法能用但笨。
3. **每帧可靠的客户区逻辑尺寸**：`设窗口尺寸` 后坐标系会跟着变（库注释如此），
   但**用户手动拖拽/进全屏**之后 `取屏幕宽`、绘制坐标系是否同步，要实测确认；
   界面重排依赖这一条，不能靠猜。
4. **像素比与字体**：现在的 `像素比` 是启动时算一次（Retina 下 800 逻辑 = 1600 物理），
   窗口跨到另一块屏（不同缩放）或进全屏后像素比会变，字体图集得按新像素比重烘焙——
   这库现在的 `建字体(路径, 参考串, 像素比)` 支持，但**重烘焙的时机要由尺寸事件驱动**。
5. **模式二所需的窗口能力**：第二窗口的创建、切换绘制目标、窗口位置/层级（谁在前）、
   每窗独立的输入焦点。渲染库 1.3.x 全是单窗口假设，这些都没有。
   替代方案是"渲染纹理"（世界画到离屏纹理再贴到窗口），也没有。
6. **全屏/最大化下的安全区**：刘海屏、Dock、菜单栏占位要给个可查询的内容区，
   不然方形区会被系统 UI 压掉一条边。
7. **显示器物理 DPI / 物理尺寸**：现在只有逻辑与缓冲两层，能算出倍率但算不出毫米；
   要做"图块物理尺寸恒定"就缺这个（连带缺"窗口跨到另一块屏时的 DPI 变化通知"）。

### 我们这边要做的配套（与上游无关，自己就能干）

- 布局**全部改成按窗口尺寸算**：现在 `窗宽=800 / 窗高=600` 是常量，
  `场偏横/场偏纵/表左/表宽/菜单坐标` 都按它写死，窗口一变就全错位。先把这些换成
  "由窗口宽高推出来的比例/居中量"，自适应才有地基。
- 方形边长取"格边的整数倍"：48 的格边下 864 已是最紧的（18 格），
  896/912/960 都能整除成整格，避免出现半格黑边。
- 尺寸变化时重算 `像素比` 与字体图集（`建字体` 重烘焙），并重建悬停命中区。

## 3. 分辨率也要分层：设计画布 / 窗口逻辑 / 物理缓冲

渲染库已经分了两层：`取屏幕宽/高`（逻辑，HIGHDPI 下 800×600 不变）与
`取渲染宽/高`（物理缓冲，Retina 下 1600×1200），并有 `转像素 / 转逻辑` 双向换算。
游戏这边要再补一层在它**下面**——**设计画布**，也就是"世界按格数算"的那层坐标。
三层各管一件事，不能混：

| 层 | 单位 | 谁在用 | 换算 |
|---|---|---|---|
| **设计画布** | 格 / 画布内的逻辑像素 | 世界区：地图格边、角色精灵、光照半径、迷雾格 | 世界边长 = 格数 × `格边`（地图03 = 18×48 = 864） |
| **窗口逻辑** | 逻辑像素（800×600 那种） | UI：对话框、菜单、存档表、字号、点击命中 | 世界缩放 `s = min(可用逻辑宽 / 世界边长, 可用逻辑高 / 世界边长)` |
| **物理缓冲** | 缓冲像素（Retina ×2） | 字体图集光栅化、贴图点采样、截图 | `像素比 = 取渲染宽() / 取屏幕宽()`；细粒度用 `转像素/转逻辑` |

规则三条：

1. **布局只在窗口逻辑层算**。UI 的 `表左/表宽/行高` 全都用逻辑像素，窗口变了重算一次即可；
   绝不用物理像素排 UI（换个屏就变样）。
2. **世界只在设计画布层算**。地图坐标、碰撞、光照半径都按格；呈现时才乘一个统一缩放 `s`。
   现在的问题恰恰是把两层粘住了：`格边 = 48` 既当美术单位又当布局单位，
   所以窗口一大，世界和 UI 只能一起被拉或一起被裁。
3. **物理层只做三件事**：字体烘焙（`建字体(路径, 参考串, 像素比)`）、贴图采样方式、
   截图输出。它不该出现在任何布局公式里。

为什么值得分：分成三层之后，"窗口自适应"才有唯一放手的地方——世界区重新算 `s` 与留边，
UI 带重新算可用宽高，字体在 `像素比` 变化时重烘焙；三件事互不牵连。
不分层的话，每加一种窗口尺寸就是一次全场改坐标。
再顺带一个已经踩过的账：`R.截图` 存的是**物理缓冲**尺寸（800×600 存成 1600×1200），
要拿像素坐标做校验就得用 `转逻辑` 反算，不能拿截图上的像素当逻辑坐标用。

### 3.1 窗口变大时：视野扩大，还是图块变粗

两种都是"合理"的，但它们回答的是不同问题：

- **图块物理尺寸恒定（≈视野扩大）**：48 逻辑格 ≈ 48/72 英寸 ≈ **1.7 cm**，Retina 只是
  1 逻辑像素对应 2 个缓冲像素，**物理尺寸不变**。窗口拉大 → 一屏装下更多格 → 看见更多。
  这条路要成立，前提是"地图比视口大"，否则最大化只是把黑边撑宽。
- **图块跟着变大（≈视野不变）**：世界整体等比放大，一屏还是那十几格，只是每格更粗。
  适合房间小、玩家想看清楚的场景。

本引擎的现实尺寸（都是 48 格边）：01 是 16×10 格（768×480）、02 是 10×8 格（480×384）、
03 是 18×7 格（864×336）。**后两张本来就比 800×600 小**，所以"恒定物理尺寸"在它们身上
不会带来视野扩大，只会得到一大片黑边——这正是需要定策略的地方。

建议的口径（按"世界是否装得下"分情况，而不是全局一刀切）：

1. **世界比可用区大** → 保持 1×，相机跟人走，窗口变大就多看到边上几格。
   但恐怖游戏里"多看到"等于变安全，所以给一条软上限：视野不超过
   `视野上限格 = 可用逻辑宽 / 格边` 的某个封顶值（当前 800 宽 = 16 格），多出来的地方
   用黑边/雾/虚焦吃掉，不白送信息。
2. **世界比可用区小**（02、03 常态）→ 走**整数倍阶梯**：`k ∈ {1, 2}`（必要时 3），
   格边取 `48 × k`，居中，余量全是黑边。像素风只有整数倍放大才不糊；
   1.5× 这种非整数倍会把像素点采成歪斜的斑，宁可不放大。
3. **不要"按窗口宽高算一个连续缩放 s"**：连续 s 在像素风里必然出现非整数倍，
   而且窗口每动 1px 就重排一次，既糊又抖。缩放只走离散阶梯，窗口连续变化只影响黑边宽度。

反过来的取舍也要记一笔：**默认固定物理尺寸（视野优先）**，把"图块变粗"做成设置项。
理由是这款是恐怖 RPG，雾、手电筒、黑边本身就是难度参数，窗口大小不该偷偷改变玩家
能看到多少；而"看着舒服"是偏好问题，给玩家一个开关比替他决定更合适。

一个必须说清的近似：真正的"毫米恒定"要显示器物理 DPI 与系统缩放比，
渲染库只有逻辑/缓冲两层（`取渲染宽/取屏幕宽` 给的是缓冲倍率，不是物理尺寸），
所以现在能做到的是**逻辑像素恒定**（≈ 1.7 cm），换不同缩放的显示器仍会漂。
要做严格毫米，得等上游补 `取显示器物理 DPI / 物理尺寸`，或自己按系统设置估。

## 4. 三档做法（按代价从小到大）

### A. 单窗口：方形世界视口 + 方形外 UI 带（今天就能做）

- 窗口做成「方形世界区 + 侧边/下边 UI 带」，世界区严格 1:1，UI 全部画在带里。
- 加一个 `F3 纯画面`：用 `设窗口尺寸(边长, 边长)` 把窗口切成正方形并隐藏 UI 带，
  退出纯画面再切回来。UP 主捕获纯画面窗口即得无 UI 方形素材。
- 代价：UI 与画面同窗，切模式要重排；UP 主若不切模式，仍得在 OBS 里裁一次。
- 优点：零桥接改动，`设窗口尺寸` 现成，输入天然归同一进程。

### B. 双进程：方形前端 + UI 后端（要点到为止）

- 前端进程只画世界（方形窗），后端进程只画 UI（大窗，位置在方形后面）。
- 键盘归属是硬约束：**前台窗口独占键盘**，所以前端收全部按键，ESC/菜单键
  通过本地 socket 或信号文件转发给后端；鼠标 hover 得把坐标转发过去。
- 还缺三个桥接入口才能摆好位置：`设窗口位置`、`设窗口置顶(false)`、屏幕坐标换算。
- 优点：两套画面真分离，UP 主各自捕获；缺点：两进程同步、启动编排、鼠标语义绕。

### C. 单进程真双窗：桥接层自己开第二个 GLFW/NSWindow（最干净、最贵）

- 一个进程、两个窗口、两套相机/绘制目标，键盘按场状态路由，鼠标按全局坐标路由。
- 需要改 `patches/渲染桥.c.macos` 并同步给上游：第二窗口创建、每窗上下文、
  窗口位置/层级、事件分发。渲染库 1.3.x 的全局状态是单窗口假设，改动面不小。
- 这是「Mac 上前面方形窗吸键、后面 UI 窗」这个点子的正解，但属于桥接层工程，
  不是原型里几行代码能糊出来的。

## 5. 输入语义（三个方案都绕不开）

- **单窗口/单进程**：ESC 归同一状态机，天然成立——按下 ESC 就是切到暂停态，
  世界区停走、UI 带出菜单，不存在"键给谁"的问题。
- **双进程**：前台窗口拿键盘、后台窗口拿不到。要么 UI 全键盘驱动（前端转发按键），
  要么 ESC 时把 UI 窗提到前台（世界窗丢焦点，等于暂停，可以接受）；
  但 UI 的鼠标 hover/点击在后台窗口上收不到，必须靠前端转发坐标。
- 结论：**UI 以键盘操作为主**最省事；鼠标只作为可选增强。

## 6. 建议的落地顺序

1. 先做 A：世界区方形化（边长 ≥ 864，建议 896）+ UI 全部挪到方形外 + F3 纯画面。
   这一步就能给 UP 主可用的方形素材，且不改桥接。
2. 拿 A 跑一段实际录像，确认"方形 + 外部 UI"是不是真要两个窗口。
3. 真要双窗再上 C（桥接层），B 只作为不想改桥接时的过渡。

## 7. 待拍板

1. 方形边长：896（世界 864 + 留边）还是 900；600 方案要压 `格边`，要不要。
2. 世界区摆位：窗口正中，还是贴左/贴右（给 UI 带留宽度）。
3. UI 带放哪：右侧竖条、底部横条，还是"纯画面时全藏、平时叠在方形外"。
4. 是否接受 A 阶段"UP 主仍需在 OBS 里裁一次"（不切 F3 的话）。
5. 模式一（UI 在窗内、窗口自适应）与模式二（UI 出窗）先做哪条；模式二是否等上游补第二窗口能力。
6. 是否现在就做"按窗口尺寸算布局"这一层（做完才能安全点亮绿键），还是先保持 800×600 固定窗口。
7. 缩放默认走"视野优先（图块物理尺寸恒定）"还是"图块变粗"，另一条是否做成设置项。
