# 天气：雨与雪

## 现状

| 版本 | 情况 |
|---|---|
| Python 版（设计提案） | `rust-bevy-endless-corridor/docs/rain_system_proposal.md`：近景大雨滴 / 远景雨丝 / 地面溅射三层，另有室内外音效差异化与配置化参数 |
| Rust 版（Bevy） | `src/environment.rs` 有 `wind_direction`、`wind_speed` 字段，也生成了雨滴实体，但 `update_rain` **只改 y**——方向字段没接线，风吹不起来 |
| 玄铁版（本项目） | **完全没有**天气效果。`主函数.xt` 只有窗口、移动、地砖、暗角、手电筒 |

所以"下雪 + 左右飘"在玄铁这一侧是从零开始，不能指望从 Rust 版继承——那里连雨的方向都还没接上。

### 原提案到底细到什么程度

`rain_system_proposal.md` 共 203 行，不是一句"加个雨"，它把参数铺得很开：

- **三档强度**（`light` / `moderate` / `heavy`），每档一组：密度 50 / 120 / 200，
  速度区间 200~400 / 300~600 / 400~800，配一个音量 0.3 / 0.6 / 0.9。
- **视觉设置**：两套雨滴颜色 `[[180,220,255,180],[200,230,255,120]]`、`splash_effects`（地面溅射开关）、
  **`wind_influence: 0.3`**——这就是"风"的来源，但它是个 0~1 的影响系数，**不是角度**。
- **音效**：室内 / 室外两份，各带 `volume`、`low_pass`、`cutoff_frequency`(800)、`spatial_blend`。
- 事件层：`RAIN_STARTED` / `INTENSITY_CHANGED` / `STOPPED` / `ENTERED_INDOOR` / `EXITED_INDOOR`。
- 实现建议：LOD 按距离调密度、相近雨滴合并成线段批量画、视锥剔除、对象池预分配、
  分辨率适配密度、`delta_time` 帧率补偿。
- 末尾还有 4 条待决策（内置默认音效？不同材质撞击声？与光照如何交互？存档要不要存降雨状态）。

上一版本文写"没有方向参数"说过头了，更正：它有**风力影响系数**，没有**角度**。
两者不是一回事——系数决定"风有多大"，角度决定"往哪边斜"。

## 设计

一个天气参数就够，雨和雪共用同一套，只是取值不同：

```json
{ "类型": "雪", "数量": 160, "方向": 12, "风力影响": 0.3, "速度": 0.6,
  "摆动幅度": 26, "摆动频率": 0.8, "大小": [2, 5], "透明": 0.75,
  "颜色": [235, 240, 255, 200], "溅射": false }
```

字段含义：

- `类型`：`雨` / `雪`。雨是直线加斜率，雪是慢速 + 正弦横摆。
- `方向`：-90~90 度，正值向右。雨靠它做出风斜；雪靠它做整体漂移的偏置。
  角度是原提案缺的那一项，加进来。
- `风力影响`：沿用原提案的 0~1 系数，乘在 `方向` 上——风大斜得多，风小几乎直落。
- `速度`：像素/秒。原提案用 200~800，单位是像素/秒，玄铁侧照抄这个量级，
  别一会儿按帧一会儿按秒。
- `摆动幅度` / `摆动频率`：只对雪有意义——每片的横向偏移 = `sin(时间 × 频率 + 相位) × 幅度`，
  相位逐片随机，整场雪就不会"齐步走"。
- `大小`：像素区间，逐片随机，近大远小靠它模拟景深（不做 z 轴，只做尺寸差）。
- `透明`：0~1。雪在暗场景里要偏灰白且低对比，太亮会盖住手电筒的暗角。
- `颜色`：RGBA。雨偏冷蓝白，雪偏灰白——原提案的两套颜色直接能用。
- `溅射`：雨落到下边缘时画一小簇短命的水花；雪关掉。

雨雪共用一套字段，只是取值和 update 规则不同：雨的 `摆动幅度` 填 0 就退化成纯斜率直线。

## 雨的三种做法，代价差得很远

"下雨"不是一个效果，是三个价位完全不同的东西。选错档不是画得难看，是做不出来。

### 一、线段雨（纯参数，本引擎取这一档）

雨滴就是一根 2~3 像素宽的短线段，长度跟速度挂钩（越快拖得越长），
整体按 `方向 × 风力影响` 斜着落。**没有任何图片**，所有变化都来自参数：
数量、速度、长度、颜色、透明度、斜度。

这是像素画风里最对的做法，也最便宜：一是不要美术资源，作者导出内容包时不用带雨图；
二是任何一档强度只是改数字；三是跟地砖、暗角、手电筒光照天然合得上。
唯一画不出来的是"雨滴本身有厚度、有水膜高光"——那已经超出像素画风的分辨率了。

### 二、贴图雨滴

每滴是一张小图（带高光、带透明边缘），位置仍然由参数生成，只有外观交给图片。
代价：一张雨滴图 + 一套图集管理 + 每种强度的尺寸/缩放；好处是看起来"湿"。

在像素画风下这条很别扭——像素雨滴的高光要跟场景分辨率严格对齐，缩放一半就糊。
真要做，也只能做**固定尺寸、整数坐标、不做缩放**的版本，等于比线段雨多花一倍工夫换一点点湿润感。

### 三、玻璃上的水珠（算法档，不要碰）

这个不是"雨滴落下来"，是**水在竖直表面上流动**：水珠会挂住、会慢慢长大、会突然下滑、
下滑时会吃掉路径上的小水珠、还会折射后面的景象。要在物理上像，需要：
黏滞/重力平衡的滑落模型、合并规则、拖尾留痕，以及折射——折射基本只能靠 shader 拿屏幕纹理做偏移。

这是着色器活儿，不是 2D 像素引擎的活儿。本项目走的是软件绘制 + 手电筒光照，
没有屏幕采样能力，这一档直接排除。真想做"窗玻璃上有水"，退一步的做法是
**在窗户图块上预先画好静态水痕**（美术资源，不是效果），成本回到第一档。

## 贴图雨滴和玻璃水珠，是不是一回事

看起来像同一件事，其实判断标准只有一条：**它有没有去采样背后的画面。**

- 贴图雨滴（不含折射的那种）：一张小图糊在半空，挡住的像素看不见了。它跟背景是**互不相干**的两层。
- 玻璃上的水珠：一滴水的视觉定义就是"把它背后的东西弄歪了"。水珠里那个倒过来的世界，
  是背景被放大、翻转、压扁之后的样子。它跟背景是**互相依赖**的。

所以一颗"贴图雨滴"和一颗"玻璃水珠"可以是同一张 PNG，差别在于**这张 PNG 里装的是不透明的颜色，
还是一套"我该怎么变形背后像素"的规则**。前者不需要配方，后者必须有配方。

沿这条线往下推，就知道为什么苹果的 Liquid Glass 看着像折射、但也不是真折射：
它做的是**采样背景 → 模糊 → 按位移贴图推开 → 加一圈镜面高光和投影**。
它不是光在水里沿着光路折射，而是"把后面的画面拿来揉一揉"。视觉上够像，物理上不是。
这也说明这类效果的门槛不在算法多深，而在**引擎有没有"读背后画面"的能力**。

本项目的渲染库（`渲染.xt`，1802 行）查过：只有 `裁剪开始`/`裁剪结束`（硬边裁剪，不是遮罩），
和 `截图(路径)`——把帧存成 PNG **文件**。没有 RenderTexture、没有 shader、没有像素回读。
所以"把背后那块像素拿来变形"这条路在玄铁版是关着的，不是难，是没有。

### 那么能不能做"看着像水珠"的

能，但用的是另一套骗术：**不采样，只画。**

一颗看起来像玻璃珠的东西，视觉上靠三样东西撑着，全都能直接画：

1. 边缘一圈亮弧（在上方/左上），一圈暗弧（在下方/右下）——这给人"凸起"的感觉；
2. 内部一点高光小亮点，位置偏上；
3. 整体半透明，颜色略偏亮或偏暗。

这三样用 `绘圆`、`绘圆线`、`绘椭圆` 叠出来就成立了，一颗的成本是几个填充圆。
它不折射背景，但暗场景里（本项目暗角 + 手电筒）本来就看不清水珠里有什么，
"亮弧 + 高光 + 半透明"骗过去绰绰有余。

代价是：水珠**不能动**。一旦要靠它表现流动、合并、拖尾，那些弧和点会跟着糊掉，
就又跌回"要读背景"的那一档了。所以静态水痕可信，动态水珠不可信。

## 镜头雨：遮挡的上限

雨滴贴在**镜头**上（离玩家眼睛最近，而不是贴在场景里的玻璃上），效果性质就变了：
它不再是"场景里在下雨"，而是"玩家的眼睛被糊住了"。这一层的取舍不是美术问题，是可玩性问题。

原则一句话：**效果可以挡光，不可以挡信息。**

具体三条：

1. **不遮交互物**。图块、光标、提示字、可拾取的东西，一律在水珠之下（后画），
   水珠先画或者只在它们之外的位置生成。黑暗里丢一个可交互物等于关卡废掉，
   这条准则在剧情侧的「写法约定」里已经写过一遍，这里是同一个道理的渲染版。
2. **不糊全屏**。镜头雨的密度上限压得很低——几滴，不是一层膜。它靠"偶尔出现"制造存在感，
   不靠"一直糊在脸上"。同时它只能出现在画面边缘和四个角，中央视野留干净。
3. **可以关**。`界面.json` 里给一个开关（`镜头雨: 关`），剧情需要时再打开。
   恐怖桥段用它很好——看不见比看得见更吓人；解谜桥段必须关掉。

### 我们的技术限制反而帮了忙

真要做到"镜头水珠让画面模糊"，必须采样背后画面做模糊——而本项目读不到背后画面（见上一节）。
所以能画出来的永远只是**几颗不透明小珠 + 高光**，天生带不来全屏模糊。
换句话说，这一档不可能做到"太真"，也就不会做到"什么都看不到"。

反过来说也成立：**如果哪天引擎真的能读背景了，第一个要防的就是这个效果做得太真。**
恐怖游戏里那种"雨糊满镜头、玩家靠蒙"的设计，属于拿效果惩罚玩家，和「惩罚判断、别惩罚路程」
是同一条底线。

## 玄铁桥接层能不能读到背景（能不能自己补上）

结论：**能，但要改桥，而且是三层都动一点。** 这不是"引擎做不到"，是"封装里没暴露"。

链路是三层：`渲染.xt`（玄铁封装，1802 行）→ `XT_*` 外函 → `渲染桥.c`（3477 行 C，直调 raylib，
且有 20 余处 rlgl 直调）→ `raylib 6.0.0`（`libraylib.darwin-arm64.a` / `linux-amd64.a`）。

raylib 6 本身这三样全都有，`raylib.h` 里就写着：

- `LoadRenderTexture(w,h)` / `BeginTextureMode` / `UnloadRenderTexture` —— 离屏渲染，把整帧画到纹理上；
- `LoadShader(文件)` / `LoadShaderFromMemory(代码)` / `BeginShaderMode` / `SetShaderValueTexture` —— 着色器与采样纹理；
- `LoadImageFromScreen()` —— 直接读屏幕缓冲，桥里**已经在用**（截图那条路径，`渲染桥.c:488`，还专门注释了取帧前必须 flush rlgl 批次）。

所以"读出来再喂回程序"在 raylib 层是现成的，缺的只是 `渲染.xt` 与 `渲染桥.c` 里的那两三个 `XT_` 函数。

### 三条路线，成本差数量级

**路线 A：整帧离屏 + 着色器采样（正统，推荐）**
每帧用 `BeginTextureMode` 把整个场景画到一张 RenderTexture，再用一个位移着色器采样这张纹理来画水珠。
- 改动量：`渲染桥.c` 加 5~6 个 `XT_`（建/删离屏纹理、开始/结束离屏、SetShaderValueTexture），
  `渲染.xt` 加对应封装，再给 `开始绘图`/`结束绘图` 一个"是否走离屏"的开关。
- 难点不在 C，在**包住整帧**：现有绘制全是立即画窗口，要在帧边界统一换目标，不能漏。
- 代价：全屏 1600×1200@60fps 多一次离屏拷贝，GPU 端很便宜；但这是全局改动，动一次所有画面都受影响，得跑全套验证。

**路线 B：不读像素，重放绘制（省一个 shader）**
场景是 2D 且绘制是确定性的，所以"背景"不一定非得读——可以把水珠那一小块区域的绘制**再执行一遍**，
画到偏移/缩放后的位置。不用 RenderTexture，不用 shader。
- 前提是绘制可重放：地砖、暗角、手电筒光照都得能在任意偏移处重算，一块 64×64 区域成本很低。
- 卡在圆形裁剪：raylib 只有矩形 scissor（`裁剪开始` 就是这个），水珠是圆的。
  没有 shader 或 alpha 蒙版就只能画矩形折射，一眼假。所以这条路最后还是要回到"蒙版乘法混合"，仍然指向 shader。

**路线 C：CPU 像素搬运（只配静止画面）**
`LoadImageFromScreen()` 是 `glReadPixels`，每帧全屏读回会直接把帧率打死。
只有"暂停/存档/读盘"这种画面静止的时刻才用得起。做动态水珠不可行。

**结论**：真要做玻璃水珠，走 A。B 是绕不开圆的，C 是性能陷阱。
A 的额外负担是**着色器文件进了分发包**——它变成一份需要随引擎版本走的资源，
和"内容包只装剧情与资产"的分层一致（shader 归引擎，归作者的内容包里不放）。

### 路线 C 的性能警告（写进对外文档时照抄这段）

> **`截图`/屏幕读回是同步的 `glReadPixels`，会让 GPU 停下来等 CPU，一帧内全屏读回可掉到个位数帧率。
> 它只适合"暂停、存档、读盘、生成缩略图"这类画面已静止的时刻，
> 不要放进任何每帧循环里，也不要拿它做动态效果。需要动态采样请走离屏渲染（RenderTexture + shader）。**

这条不只是代码注释——凡是调用这条路径的公开函数，说明文档里都要写明，且默认关闭/懒加载，
不能做成"一调用就生效"的默认行为。

## 加 shader 是不是等于"把玄铁做成游戏引擎"

不是。这条界线值得写清楚，否则每次提需求都要重新争一遍。

**渲染库负责"怎么把东西画到屏幕上"，游戏引擎负责"世界里有什么、怎么运转"。**

- 渲染库提供的是**手段**：窗口、像素、线段、矩形、纹理、字体、相机、混合模式。
  加一个 shader，只是把显卡本来就有的能力经由封装露出来——它仍然是一个"怎么画"的工具，
  不会因此长出场景图、实体表、组件系统、物理、资源调度、存档这些"世界模型"。
- 玄铁"不做游戏引擎"说的是**不做那一整套世界模型**，不是"不许碰底层画图能力"。
  两者不冲突，甚至相反：底层能力越完整，上层引擎越好做。
- 佐证：`渲染.xt` 里有 `设置相机3D`、`进入3D`/`退出3D`、`绘立方体`、`绘球体`、`绘地面网格`、
  `绘直线3D`、`推矩阵`/`弹矩阵`——**库给了相机和图元**，作者拿它们自己搭 3D 游戏。
  有相机不等于有引擎；引擎是他拿相机写出来的那个东西，不是相机本身。

所以"让渲染库功能更完善"是正当的：补的是画图手段，不是替谁做引擎。
本项目那个剧情驱动引擎、内容包分层、RPG 规则，全在我们这一层，跟渲染库无关。

**现状核对**：`渲染.xt` 全文 1802 行，`shader`/`着色` 命中 **0** 次——它现在确实没有 shader 概念，
纯"一层一层往上叠立即绘制"。要 shader 只能从 `渲染桥.c` 那层加 `XT_` 函数再往上封装。

## 路线 A / B 的大白话版

上一节写得偏技术，换成两句人话：

- **A（离屏 + 采样）= 先拍照，再修照片。**
  这一帧不直接画到窗口，先画到一张"暂存图"上；然后要画水珠的地方，**从这张暂存图上取一块**
  （翻转、放大、挪一点），贴回水珠的位置。因为"取一块并变形"每个像素都要算，所以要 shader。
- **B（重放绘制）= 不拍照，照着再画一遍。**
  水珠那一小块背景，把绘制代码**重新跑一次**，画到偏一点的位置。省掉暂存图，也省掉 shader，
  但"只取一个圆形区域"这件事它做不到——库只能按矩形裁剪，所以水珠只能是方的，一眼假。

一句话记：**A 是"读现成的"，B 是"再画一遍"。** A 贵在要改桥、要装着色器文件；B 便宜在圆形圆不起来。

### 改哪个基线（重要，别改错）

本机安装的 `渲染` 包是 **v1.3.11**（`渲染.xt` 1802 行 / `渲染桥.c` 3477 行），
公开仓库 `gitcode.com/MARKJY/XuanTieRendering` 只有 **2175 行 C / 772 行封装**——
**上游公开仓库比本机包旧**（`tiepm.toml` 里版本号还写着 1.3.2，而 1.2.5~1.3.11 全部
tag 都指向同一个 commit）。所以：

- **不要对着上游仓库改**，会退掉字体图集、隐藏窗口、3D 图元这些已有能力；
- 正确基线是**本机已安装的那份源码**（`~/Library/Caches/xtl/core/darwin-arm64/xtc-package/lib/渲染/`，
  里面 `渲染桥.c` 和 `.o` 都在），复制一份到工作目录改，重编 `.o`；
- 编译已实测可行：`cc -c 渲染桥.c -o 渲染桥.o -I. -O2`（本机零报错）；
- 上游那份建议只用来**报 issue**（说明公开仓库落后于分发包），不要拿它当基线。

## 实现要点（玄铁侧）

- 粒子是一个数组：`{ x, y, 速度, 相位, 大小, 颜色 }`，进场景时按 `数量` 生成一次；
  原提案的"对象池预分配"就是这个意思——不每帧新建对象，只改数值。
- 每帧：`y += 速度 × dt`；`x += sin(相位 + 时间×频率) × 幅度 + 方向 × 风力影响 × dt`；
  越界（y > 下边缘）就回收到顶部随机 x。
- **粒子是代码画的，不用位图**：雨画成两三像素宽的短线段（长度按速度给，越快越长），
  雪画成单个像素块或 2×2 小方点。原提案"内存管理"一节提到雨滴贴图缓存，那是可选项，
  在这个画风下反而是负担——一整套贴图要管图集、要管缩放。
- 颜色和透明直接走绘制的顶点色参数（实际接口名 grep `lib/渲染/渲染.xt` 确认，不要凭记忆写）。
- 数量控制在 100~200 之间，对齐原提案 `moderate` 档的 120。文本/地砖本来就不重，
  粒子不该成为新瓶颈；原提案的 LOD 和视锥剔除在 2D 小窗口里没必要，跳过。
- `delta_time` 帧率补偿要保留：不按帧算位移，按秒，否则高刷屏上雪会飞。

## 与剧情的关系

天气属于渲染层，写在 `剧情/界面.json` 里（按幕或场景挂），由 `主函数.xt` 读入后生效；
剧情 JSON 不直接控制粒子，只声明"这一场要雪"。这样换剧情不用改引擎，关掉天气也不改剧情。

## 验证口径

渲染程序只能跑窗口验证：`rvs scripts/test-macos.rvs` 会构建并跑 4 秒后自动关闭。
判断标准是肉眼——雪片有没有左右飘、有没有齐步走、暗角里还看不看得见、帧率有没有掉。
**跑这个会短暂弹出一个窗口**，测试前先说一声。
