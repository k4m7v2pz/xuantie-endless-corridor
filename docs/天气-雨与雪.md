# 天气：雨与雪

## 现状

| 版本 | 情况 |
|---|---|
| Python 版（设计提案） | `rust-bevy-endless-corridor/docs/rain_system_proposal.md`：近景大雨滴 / 远景雨丝 / 地面溅射三层，另有室内外音效差异化与配置化参数 |
| Rust 版（Bevy） | `src/environment.rs` 有 `wind_direction`、`wind_speed` 字段，也生成了雨滴实体，但 `update_rain` **只改 y**——方向字段没接线，风吹不起来 |
| 玄铁版（本项目） | **完全没有**天气效果。`主函数.xt` 只有窗口、移动、地砖、暗角、手电筒 |

所以"下雪 + 左右飘"在玄铁这一侧是从零开始，不能指望从 Rust 版继承——那里连雨的方向都还没接上。

### 原提案到底细到什么程度

`rain_system_proposal.md` 共 203 行，不是一句"加个雨"，它把参数铺得很开：

- **三档强度**（`light` / `moderate` / `heavy`），每档一组：密度 50 / 120 / 200，
  速度区间 200~400 / 300~600 / 400~800，配一个音量 0.3 / 0.6 / 0.9。
- **视觉设置**：两套雨滴颜色 `[[180,220,255,180],[200,230,255,120]]`、`splash_effects`（地面溅射开关）、
  **`wind_influence: 0.3`**——这就是"风"的来源，但它是个 0~1 的影响系数，**不是角度**。
- **音效**：室内 / 室外两份，各带 `volume`、`low_pass`、`cutoff_frequency`(800)、`spatial_blend`。
- 事件层：`RAIN_STARTED` / `INTENSITY_CHANGED` / `STOPPED` / `ENTERED_INDOOR` / `EXITED_INDOOR`。
- 实现建议：LOD 按距离调密度、相近雨滴合并成线段批量画、视锥剔除、对象池预分配、
  分辨率适配密度、`delta_time` 帧率补偿。
- 末尾还有 4 条待决策（内置默认音效？不同材质撞击声？与光照如何交互？存档要不要存降雨状态）。

上一版本文写"没有方向参数"说过头了，更正：它有**风力影响系数**，没有**角度**。
两者不是一回事——系数决定"风有多大"，角度决定"往哪边斜"。

## 设计

一个天气参数就够，雨和雪共用同一套，只是取值不同：

```json
{ "类型": "雪", "数量": 160, "方向": 12, "风力影响": 0.3, "速度": 0.6,
  "摆动幅度": 26, "摆动频率": 0.8, "大小": [2, 5], "透明": 0.75,
  "颜色": [235, 240, 255, 200], "溅射": false }
```

字段含义：

- `类型`：`雨` / `雪`。雨是直线加斜率，雪是慢速 + 正弦横摆。
- `方向`：-90~90 度，正值向右。雨靠它做出风斜；雪靠它做整体漂移的偏置。
  角度是原提案缺的那一项，加进来。
- `风力影响`：沿用原提案的 0~1 系数，乘在 `方向` 上——风大斜得多，风小几乎直落。
- `速度`：像素/秒。原提案用 200~800，单位是像素/秒，玄铁侧照抄这个量级，
  别一会儿按帧一会儿按秒。
- `摆动幅度` / `摆动频率`：只对雪有意义——每片的横向偏移 = `sin(时间 × 频率 + 相位) × 幅度`，
  相位逐片随机，整场雪就不会"齐步走"。
- `大小`：像素区间，逐片随机，近大远小靠它模拟景深（不做 z 轴，只做尺寸差）。
- `透明`：0~1。雪在暗场景里要偏灰白且低对比，太亮会盖住手电筒的暗角。
- `颜色`：RGBA。雨偏冷蓝白，雪偏灰白——原提案的两套颜色直接能用。
- `溅射`：雨落到下边缘时画一小簇短命的水花；雪关掉。

雨雪共用一套字段，只是取值和 update 规则不同：雨的 `摆动幅度` 填 0 就退化成纯斜率直线。

## 雨的三种做法，代价差得很远

"下雨"不是一个效果，是三个价位完全不同的东西。选错档不是画得难看，是做不出来。

### 一、线段雨（纯参数，本引擎取这一档）

雨滴就是一根 2~3 像素宽的短线段，长度跟速度挂钩（越快拖得越长），
整体按 `方向 × 风力影响` 斜着落。**没有任何图片**，所有变化都来自参数：
数量、速度、长度、颜色、透明度、斜度。

这是像素画风里最对的做法，也最便宜：一是不要美术资源，作者导出内容包时不用带雨图；
二是任何一档强度只是改数字；三是跟地砖、暗角、手电筒光照天然合得上。
唯一画不出来的是"雨滴本身有厚度、有水膜高光"——那已经超出像素画风的分辨率了。

### 二、贴图雨滴

每滴是一张小图（带高光、带透明边缘），位置仍然由参数生成，只有外观交给图片。
代价：一张雨滴图 + 一套图集管理 + 每种强度的尺寸/缩放；好处是看起来"湿"。

在像素画风下这条很别扭——像素雨滴的高光要跟场景分辨率严格对齐，缩放一半就糊。
真要做，也只能做**固定尺寸、整数坐标、不做缩放**的版本，等于比线段雨多花一倍工夫换一点点湿润感。

### 三、玻璃上的水珠（算法档，不要碰）

这个不是"雨滴落下来"，是**水在竖直表面上流动**：水珠会挂住、会慢慢长大、会突然下滑、
下滑时会吃掉路径上的小水珠、还会折射后面的景象。要在物理上像，需要：
黏滞/重力平衡的滑落模型、合并规则、拖尾留痕，以及折射——折射基本只能靠 shader 拿屏幕纹理做偏移。

这是着色器活儿，不是 2D 像素引擎的活儿。本项目走的是软件绘制 + 手电筒光照，
没有屏幕采样能力，这一档直接排除。真想做"窗玻璃上有水"，退一步的做法是
**在窗户图块上预先画好静态水痕**（美术资源，不是效果），成本回到第一档。

## 实现要点（玄铁侧）

- 粒子是一个数组：`{ x, y, 速度, 相位, 大小, 颜色 }`，进场景时按 `数量` 生成一次；
  原提案的"对象池预分配"就是这个意思——不每帧新建对象，只改数值。
- 每帧：`y += 速度 × dt`；`x += sin(相位 + 时间×频率) × 幅度 + 方向 × 风力影响 × dt`；
  越界（y > 下边缘）就回收到顶部随机 x。
- **粒子是代码画的，不用位图**：雨画成两三像素宽的短线段（长度按速度给，越快越长），
  雪画成单个像素块或 2×2 小方点。原提案"内存管理"一节提到雨滴贴图缓存，那是可选项，
  在这个画风下反而是负担——一整套贴图要管图集、要管缩放。
- 颜色和透明直接走绘制的顶点色参数（实际接口名 grep `lib/渲染/渲染.xt` 确认，不要凭记忆写）。
- 数量控制在 100~200 之间，对齐原提案 `moderate` 档的 120。文本/地砖本来就不重，
  粒子不该成为新瓶颈；原提案的 LOD 和视锥剔除在 2D 小窗口里没必要，跳过。
- `delta_time` 帧率补偿要保留：不按帧算位移，按秒，否则高刷屏上雪会飞。

## 与剧情的关系

天气属于渲染层，写在 `剧情/界面.json` 里（按幕或场景挂），由 `主函数.xt` 读入后生效；
剧情 JSON 不直接控制粒子，只声明"这一场要雪"。这样换剧情不用改引擎，关掉天气也不改剧情。

## 验证口径

渲染程序只能跑窗口验证：`rvs scripts/test-macos.rvs` 会构建并跑 4 秒后自动关闭。
判断标准是肉眼——雪片有没有左右飘、有没有齐步走、暗角里还看不看得见、帧率有没有掉。
**跑这个会短暂弹出一个窗口**，测试前先说一声。
