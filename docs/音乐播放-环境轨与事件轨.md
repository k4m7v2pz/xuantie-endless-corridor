# 音乐播放：环境轨 + 事件轨（设计）

> 状态：设计稿，**未实现**。前置依赖是渲染库补三个入口（见「技术现状」）。
> 适用两套前端：2D 渲染程序（`主函数.xt`）与 TUI 剧情播放器（`文字剧情/**`）。

## 1. 要解决的是什么

地下室这类场景常驻一首中性、悬疑但不第三的**环境音乐**；某个房间触发追逐战，换成
**追逐专用音乐**；玩家逃出来，回到环境音乐。

要的听感是：**环境音乐从它本该在的位置接着播**，不是从头开始。

- 如果环境曲很长（3 分钟），玩家在 1 分 20 秒进入追逐，又跑了 40 秒——出来时它应该在
  约 2 分 00 秒的位置继续，而不是回到 0 秒。
- 玩家不该感觉到"音乐断了、又重新来了一遍"。追逐期间的 40 秒，环境曲应该是"没在出声，
  但仍在走"。

这条需求的本质是：**两轨共用一个持续的时间线，事件轨只是暂时把它压下去。**

## 2. 结论先说：别"停—重播"，要"音量压到 0"

很容易写成的错误实现是：追逐开始 → `停音乐流(环境)`，播追逐；追逐结束 → 重新
`播音乐流(环境)`。

`停音乐流` 内部是 `StopMusicStream`，**会把播放位置归零**。再播就是重头，正好是用户
不想要的那种突兀。

正确实现只有一个：

| 阶段 | 环境轨 | 事件轨 |
|---|---|---|
| 进场景 | 播，音量 1 | — |
| 追逐开始 | **继续播，音量 0**（解码与计时照常走） | 播，音量淡入到 1 |
| 追逐中 | 音量 0，时间线继续前进 | 音量 1 |
| 逃出 | 音量淡回 1（**位置正好接上**） | 淡出，停并释放 |
| 换场景 | 换曲：新曲淡入，旧曲淡出后释放 | — |

关键点：**"没出声但仍在走"= 音量 0，不是停播。** 这也是 raylib 天然支持的做法
（`SetMusicVolume(0)` 时 `UpdateMusicStream` 仍然推进 `ctx->position`）。

## 3. 技术现状（实测，渲染库 1.3.11）

`lib/渲染/渲染.xt` 里音乐流只有五个入口：

```
加载音乐流(文件)       XT_LoadMusicStream
播音乐流(句柄)         XT_PlayMusicStream
更新音乐流(句柄)       XT_UpdateMusicStream   // 每帧必须调，否则断续/无声
停音乐流(句柄)         XT_StopMusicStream     // 会归零
释音乐流(句柄)         XT_UnloadMusicStream
```

raylib 本身还有 `SetMusicVolume` / `PauseMusicStream` / `ResumeMusicStream` /
`SeekMusicStream` / `GetMusicTimePlayed` / `GetMusicTimeLength`，
**渲染桥里一个都没导出**。所以第 2 节那套现在做不成——没有音量接口就没有 duck。

### 需要补的入口（建议给上游）

```xt
公 函 设置音乐音量(句柄, 音量)      // SetMusicVolume，0–1
公 函 暂停音乐流(句柄)             // PauseMusicStream（可选，见下）
公 函 续播音乐流(句柄)             // ResumeMusicStream
公 函 音乐进度(句柄): 小数          // GetMusicTimePlayed，秒，调试与验证用
公 函 音乐时长(句柄): 小数          // GetMusicTimeLength，秒
公 函 定位音乐(句柄, 秒)            // SeekMusicStream，仅跨幕恢复/跳时用
```

- **`设置音乐音量` 是唯一硬依赖**，没有它这套做不出来。
- `暂停/续播` 可选：注意 raylib 暂停时**时间线也停**，所以追求"计时继续走"时反而
  应该用音量 0 而不是暂停。暂停只适合"玩家开着菜单、真要冻结音乐"那种场景。
- `音乐进度` 用来验证"接上"到底接上没有（见第 7 节），不是演出功能。
- `定位音乐` 只在跨幕/存档恢复时用，日常切轨不应该靠它——靠它就会听见一首曲从中间
  突然开始，比接续更突兀。

**分叉风险**：`patches/渲染桥.c.macos` 是同步自上游内置桥的副本，不宜长期本地加料。
两条路，二选一：（a）提上游 PR 加这几个入口；（b）先在本地补丁里加，并在文件头
明确标注"本地扩展，等待上游合入"，合入后立即改回同步。

## 4. 引擎层结构：一个双槽音乐总线

不看具体曲目，引擎只维护两个"槽"和一组音量渐变：

```
环境槽：句柄、目标音量、当前音量
事件槽：句柄、目标音量、当前音量、是否在播
每帧：
  更新音乐流(环境句柄)      // 两个都要调，否则那条解码断供
  更新音乐流(事件句柄)
  向目标音量线性逼近（按 dt 算，不用固定步长）
```

对外只暴露四个动作，剧情与内容包不需要知道别的：

| 动作 | 语义 |
|---|---|
| `切场景音乐(键)` | 常驻轨。同一个键重复调用是空操作（**这很重要**：同一场景内多个节点都写它不会重播） |
| `起事件音乐(键, 秒?)` | 临时轨，环境轨压到 0 |
| `收事件音乐()` | 事件轨淡出释放，环境轨音量回 1 |
| `复位音乐()` | 幕/章节切换、玩家死亡、读档时用：两槽全停全释，时间线重来 |

渐变建议值（听感调过的起点，可改）：

- 追逐起：事件轨淡入 **0.15 s**（要"突然起来"），环境轨压到 0 用 **0.2 s**。
- 追逐收：事件轨淡出 **0.5 s**，环境轨回 1 用 **0.8 s**（回来要"慢慢浮上来"）。
- 普通换场景：旧曲淡出 0.4 s，新曲淡入 0.6 s；两段可以重叠一点，别留静默空档。

**不要搞成 0 个帧的硬切**：音乐硬切会在听觉上留下一个"咔"，比突兀更明显。

## 5. 数据侧：剧情/内容包怎么表达

引擎不懂"地下室""追逐"，只认上面四个动作。所以剧情 JSON 只写**语义键**，不写文件路径：

```json
"音乐": { "场景": "地下室" }              // 只在跨场景节点写一次
"音乐": { "事件": "追逐" }                // 事件节点写事件键
"音乐": { "事件": "停" }                  // 显式收；也可以由节点类型自动收
```

- 键到文件的映射放在内容包的 `音乐表.json`（和 `音效表.json` 同一个思路），
  换曲不用改剧情、不用改引擎。
- **自动收的时机**要定死：`类型` 为 `结局`、或节点带 `场景` 切换、或玩家失败重试时
  一律先收事件轨。否则玩家被抓了还在听追逐曲、进了结局曲下面还垫着。
- 同一幕里反复出现的"进房间—出房间"不该触发换曲，所以场景键应当**按地点命名**
  （`地下室`/`走廊`），不是按节点命名（`进入地下室`/`离开地下室`）。

素材提示：音乐若用 `assets/audio/music/suno_ai/` 里的示例曲，仅限个人非商业；
长音频用 ogg（长音频不进 wav），细则见 `docs/内容包与引擎分离.md`。

## 6. 边界与已知坑

- **音池上限 32**，音乐与音效共用句柄空间（1 起），长曲别开一堆。
- **循环**：raylib 默认单次播放完会停，循环要靠反复 `播音乐流`（会归零）或上游补
  `设置音乐循环`。环境曲本来长，够撑一幕；真要循环播放得列入上游待补。
- **不能在玄铁里合成/解码长音乐**：浮点逐样本内存线性上涨（约 709 字节/轮），
  且库没有流式回调。长音乐一律"外部生成文件 + `加载音乐流` 播"。
- **TUI 播放器**目前只有短音效（`加载音效`/`播音效`），没有接音乐流；它的主循环是
  行驱动的阻塞等待，要接这套总线得在等待输入的空转里调 `更新音乐流`，属于后续工作。
- **每帧更新两条流**：漏掉一条就是"另一条没声/断续"，这是最容易犯的错。

## 7. 最小验证步骤（API 到位后照此验）

1. 准备两条 ogg：环境曲 A（≥60 s，便于计时）、事件曲 B（≥10 s）。
2. 进场景播 A，记 `T0`；第 10 s 起事件 B（A 音量压 0）。
3. 第 15 s 收事件（A 音量回 1），立刻打点 `音乐进度(A)`，应约为 **15 s**，
   而不是 0 或 5。
4. 再对 B 打 `音乐进度(B)`，应在 5 s 左右（它自己的时间线独立）。
5. 对照实验：用"停—重播"实现跑同一流程，听感差异应当明显（这一步是给人听的，
   跑之前先说播什么、几段、多长）。
6. 跨幕/失败重试：`复位音乐` 后两槽都归零，不能出现上一幕的曲继续垫在下一幕下面。
