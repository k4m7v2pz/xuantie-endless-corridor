# 事件树视图设计（叙事图谱 / Event Tree）

> 状态：设计稿（v0.1），尚未实现。本文档定义目标、交互形态、数据结构与时间预估模型，
> 供后续在玄铁版「无尽回廊」中分阶段落地。

## 1. 定位

给玩家一张**自己探索出来的**剧情结构视图，回答三个问题：

1. **我在哪？** 当前节点在整个叙事结构里的坐标。
2. **前面还有什么？** 还有多少可探索的通路、还剩多长。
3. **哪些已经永久错过？** 避免"回头重开"的挫败。

它**不是**完整剧情剧透，也不是逐句台词预览。展示的是玩家已探测到的部分，而非设计师原图。

## 2. 核心判断：大节点不是"节点"，是"刻度"

玩家在大节点这一层想要的不是拓扑，而是**进度标量**（"我前面还有多久"）；
小节点承载的才是**选择**（"我有哪几条路"）。两者认知诉求不同，混在同一视图必然乱。

因此采用 **一维主轴 + 局部二维展开**（focus + context）：

```text
L0 幕视图（默认，永远只是一条横线）
  [幕一 ✓]──[幕二 ✓]──[幕三 ●]──[幕四 ◇]──[幕五 ?]──[≈?]
   （方框里显示的是「幕名」展示文本；内部编号一律整数 1..7）
   ← 已体验 ───────────── 当前 ────── 未知（有界推测） ─→

L1 场景视图（点开「幕三」才出现）
                 ┌─ 场景3-2a ─┐
  场景3-1 ── 场景3-2 ── 场景3-3 ── 场景3-4（幕末）
                 └─ 场景3-2b ─┘
```

## 3. 三层颗粒度

| 层 | 单位 | 职责 | 何时可见 |
|---|---|---|---|
| **幕 Act** | 叙事大段落（建议 5~9 个） | 进度刻度、剩余量预估 | 永远可见，线性横排 |
| **场景 Scene** | 一段闭环剧情单元 | 选择与分支、**时间统计基本单位** | 仅所属幕展开时 |
| **节拍 Beat** | 单次选择、单条件判定 | 细节 | 默认隐藏，hover/详情面板 |

**硬规则：同一屏同时可见的分支宽度 ≤ 3。**
每次展开只显示当前节点 ±1 层，绝不同时铺开整个子树。
乱不乱取决于同时可见的分支宽度，而非节点总数。

### 3.1 场景层的「主线 + 挂载点」

幕内不要真做成树，做成：

- 一条**必然走过的场景序列**横排（场景3-1 → 3-2 → 3-3 → 幕末）；
- 分支是挂在某个场景**上方/下方**的子条，走完回归主线（回流型），或标记为脱离（分流型）；
- 走完后子条收拢成角标，不留在画面上。

即使幕内有 10 个场景、8 条分支，可见结构仍是「一条线 + 几个括号」。

## 4. 线性可行的前提：幕级分叉被强约束

L0 一旦出现三四个并列轨道，玩家无法把多条并行剩余量加成一个标量，预估立刻失效。故：

- **幕级分叉全流程最多 1~2 次，且必须是显式 Y 形分叉**（如"第一章末二选一"），
  分叉后各自再收束成一条线；
- 绝大多数选择只影响**幕内场景序列**，不影响幕的走向与数量；
- 玩家无论怎么选，都会推进到下一个幕。

副作用（正面）：幕视图的线性直接定义了"叙事总量"——看到 7 个格子即知是 7 幕规模。

### 4.1 幕边界必须人工标记，不自动聚类

自动聚类会让边界随事件增删漂移，玩家上次记住的"幕三"变成"幕四"，记忆错位。
幕边界是设计资产：每个事件只加「所属幕」+「幕内序号」两个字段，幕视图纯靠它们渲染。

## 5. 节点状态与视觉语义

| 状态 | 视觉 | 含义 |
|---|---|---|
| 已完成 | 绿色实框 | 已走完 |
| 已发现未进入 | 浅灰实框 | 玩家知道存在，未触发 |
| 已知存在但未知内容 | 半透明虚框 | 推测/暗示，未确认 |
| 当前 | 高亮描边 | 玩家所在节点 |
| 已绕过 | 蓝灰，连线虚线 | 可选挑战未完成，主线已推进 |
| 永久关闭 | 暗红/暗灰，连线枯萎 | 错过、分支已封死 |

- **连线**：一条线 = 一条可行通路，可附极简条件标记（选择 A / 物品持有 / 好感达标 / 时间窗口）。
  条件未满足时显示"条件未知"，不显示具体条件文本。
- **折叠**：已完成的旧枝可收拢，只看前方，避免画面爆炸。
- **锚点标记**：允许玩家手动标记节点，便于回忆当时的选择。

## 6. 未知节点的渲染规则（防剧透边界）

- 未知节点**不能以实框出现**；
- 未知幕最多预渲染 **2 个**（紧邻的下一个 + 再下一个的轮廓）。再多，未知感被稀释，
  且布局会随剧情推进剧烈抖动；
- 预渲染用虚框 + 占位符号，**不写任何标题，不给未知幕编号**——编号会把未知变成清单/KPI，破坏悬念；
- 不提前暴露"这个选择通向哪个结局"；
- 关键反转节点：即使前置满足，也等到触发后才补全节点与连线；
- 隐藏结局节点描述保持模糊，保留悬念。

## 7. 剩余时间预估模型（按现实时间，滚动校准）

### 7.1 结论先行

目标变量不是"这个节点设计上多长"，而是**"这个玩家现实里还要多久才会到达下一个节点"**。
作者手填时长对单个玩家基本无效：同一段耗时方差极大（跳过文本 vs 逐行读、一眼看穿 vs 绕图三圈），
跨玩家平均对谁都不准。唯一有效基准是这个玩家自己的历史。

**并且：读文本、观察环境、跑图、解谜反复绕圈的时间必须全部计入。**
这些不是噪声，恰恰是真实到达时间的主体，也是方差的主要来源。
剩余时间预估若把它们剔掉，算出来的数字与玩家体感完全无关。

### 7.2 时间计入规则（关键修正）

按"游戏是否在推进"三分，**只有第三类剔除**：

| 类别 | 例子 | 计入 |
|---|---|---|
| 积极游玩、无输入 | 读文本、观察、跑图、解谜反复绕、被吓住盯着屏幕 | **计入** |
| 游戏未推进 | 窗口失焦/最小化、系统或暂停菜单、存档读档界面 | 不计（游戏时钟本就没走） |
| 人不在 | 离开座位、吃饭、睡觉、切去看别的 | 剔除 |

第三类的判据**不是"没有按键"**，而是同时满足：窗口有焦点 + 超过长阈值（建议 8~10 分钟）
+ 期间**零代理人活动**（角色零位移、视角零变化、无任何引擎事件）。
单靠输入间隔判定会误杀解谜思考——玩家盯着一条线索五分钟不动手是常态。

### 7.3 跑图时间不靠猜，用实测步速算

跑图成本可由"玩家实测移动速度 × 地图路径长度"给出**下限**，不必拿作者基线估：

```text
移动下限 = 路径长度(格) / 玩家实测步速(格每秒)
```

路径长度由地图寻路得出；玩家实际绕路的额外长度另计（见 7.5）。
这条把跑图从"猜"变成"算"，是整个模型里唯一能精确建模的分量。
同一玩家的实测步速取自他跑过的所有路段（像素/格每秒），不需要额外采集。

### 7.4 两个分量分开建，别混成一个数

```text
预估现实到达时间 = 移动分量（可算，见 7.3）
                 + 认知分量（阅读 + 解谜，不可直接测）
```

认知分量是长尾来源——同一个谜题有人三分钟、有人一小时。它不能点估计，必须用分布。

### 7.5 分布而非点估计

解谜耗时右尾极长，按**对数正态**处理：

```text
x_i     = ln(a_i / e_i)                 # 比值取对数，压掉长尾
节奏对数 = 近期加权中位数(x_i)            # K = 5~8 个已完成场景
离散    = 标准差(x_i)
预估_中位 = exp(节奏对数) * Σ e_剩余
预估_九成 = exp(节奏对数 + 1.28*离散) * Σ e_剩余
```

- 用对数空间的中位数，**绝对不要用算术平均**——一次卡关一小时会把算术平均永久拉偏；
- 样本 `n < 3` 时不做点估计，直接给区间 `[0.6x, 3x]` 或"约十几分钟"；
- 输出两个数：**"大概 X 分钟"（中位情形）** 与 **"如果卡住，可能 Y 分钟"（最坏情形）**。
  恐怖解谜题材里 最坏情形 比 中位情形 更有用——玩家真正想知道的是"今晚能不能打完这一章"。

### 7.6 卡关是一次性事件，别污染速度系数

- **同一场景重复进入**（知道谜底后重走）耗时骤降，单独计数，不进节奏系数的样本池；
- 首次卡关时长按"该谜题类型的全玩家卡关率"做先验，不计入个人固有速度；
- 多周目默认用最近一周目样本，历史周目只作 最坏情形 参考。

### 7.7 采样与截尾

```text
进入场景 -> t0
离开场景 -> t1
a_i = t1 - t0 - 剔除段(7.2 第三类)
```

**保留原样，不做上限截尾**——卡关一小时是真实数据，必须进分布，靠 7.5 的对数变换吸收长尾。
只对**非现实因素**做排除：窗口失焦累计超过总时长一半的样本标为不可信并弃用。

### 7.8 UI 表达

- 幕视图：当前幕下方标「进行中 · 已 12 分钟」；
  已完成幕**不标逐节点现实耗时**——逐条显示会变成自我审判，玩家会开始跟自己的时间较劲；
- 全局角落小字：「大概还要 40 分钟；如果卡住，可能 1 小时半」；
- **不要**用"还有 3 个节点"这种引擎内部计数替代时间——玩家对齐的是时间成本。

## 8. 数据结构草案（中文字段命名）

玄铁是中文编程语言，标识符一律用中文，不写英文蛇形。
字段名、函数名、常量名全部中文；布尔函数沿用现有习惯加问号后缀（如 `撞墙?`）。

```text
场景 = {
  编号:         唯一标识
  所属幕:       幕.编号（整数，人工标记）
  幕内序号:     整数
  类型:         对话 | 探索 | 解谜 | 战斗 | 过场
  标题:         摘要标题（场景视图展示用，非台词）
  概括:         一句话
  设计意图:     为什么这样设计、答案是什么含义（给 agent 与卡关玩家看）
  答案:         解谜答案明文（可直接改来放宽难度）
  前驱:         [场景.编号]        # 哪些场景能到达它
  后继:         [场景.编号]        # 它的出口
  通行条件:     { 选择项: [...], 物品: [...], 标记: [...], 时限: ? }
  去向:         回流 | 分流 | 绕过
  作者基准分钟: 可缺省（缺省时用 类型先验）
  剧透级别:     正常 | 延迟揭示 | 模糊
  路径长度升:   整数（可缺省，用于移动分量下限）
}

幕 = {
  编号:       整数（排序、比较、计数一律用它；禁止用中文数字或字符串存序号）
  幕名:       展示文本（如「第三幕 · 对立面」），只给人看，不参与任何计算
  标题已知?:  真/假
  入口场景, 收束场景, 类型先验分钟: 整数
}

所有数值字段一律整数（玄铁 JSON 会把小数退化成 `"object"`，见 9.2）；
比例类字段用千分制整数表达。

运行态（存档内，不进设计数据）:
  已发现:     集合<场景.编号>
  状态:       映射<场景.编号, 未发现|已发现|进行中|已完成|已绕过|永久失效>
  采样:       映射<场景.编号, {原值, 计入值, 次数, 是否首次}>
  实测步速:   格每秒（全局一个，取自玩家跑过的所有路段）
  节奏对数:   数值
  离散:       数值
```

### 8.1 数值与中文的边界（实测）

中文只用在三类地方，数值一律阿拉伯数字：

| 什么 | 允不允许中文 | 说明 |
|---|---|---|
| JSON 键名 / 变量名 / 函数名 | ✅ 中文 | 玄铁标识符支持中文，JSON 键实测原样保留 |
| 展示文本（幕名、标题、概括、设计意图） | ✅ 中文 | 给人看的内容随便写 |
| **数值** | ❌ 只能用整数 | 汉字数字不是数值，见下 |

实测（2026-11-18，`xtl pao`）：

```text
设 甲 = 三
  → 编译错误: [主函数.xt 行:2, 列:7] 未知标识符 '三'

示("3" == 3)    → 假        // 字符串与整数不互通，别指望隐式转换
示("10" - "3")  → 7         // 减法会自动转数值（规则不统一，不可依赖）
```

三条推论：

1. **幕编号、幕内序号、各类分钟数、千分比，全部用整数**。
   中文数字只许出现在 `幕名` 这类展示字段。
2. **节点 ID（`"3-2"`）是标识符，不是数值**。排序、比较、算剩余量一律用
   `所属幕` + `幕内序号` 两个整数字段，**不要去解析 ID 字符串**。
3. 排序逻辑不要依赖字符串数字的隐式比较（`==` 不转换、减法转换，规则不一致）。

命名对照（防止后续有人写回英文）：`所属幕`（原 act_id）、`作者基准分钟`（原 author_minute）、
`剧透级别`（原 spoil_level）、`节奏对数`（原 pace_ratio）、`路径长度升`（原 path_len）。

## 9. 剧情数据层是配置文件，不是源码

### 9.1 引擎与内容必须分离

- **引擎**：玄铁源码，编译成二进制，玩家拿到的是 `corridor` 这样的可执行文件；
- **剧情**：JSON 配置文件，运行时加载。

传播现实是：玩家之间传的是二进制 + 运行必需的配置文件，**源码基本不会外流**。
所以剧情若写在 `.xt` 源码里，玩家永远看不到——这会直接毁掉 9.3~9.5 想做的一切。

**结论：剧情、事件树、幕划分一律放在 JSON 配置里；`.xt` 只承载引擎逻辑。**

附带好处：

- 改剧情不必重新编译，可热加载；
- 写剧情的人和写引擎的人可以完全分开，互不干扰；
- 玩家可以自制内容（mod），项目天然可扩展；
- agent 改剧情只改 JSON，不必碰引擎源码，也不可能改坏引擎。

一句话：**引擎提供通用可复用的框架，剧情配置指挥引擎怎么走。**

### 9.2 为什么是 JSON（含玄铁实测结论）

玄铁**原生支持 JSON，而且是语言内置关键字，不需要装任何库**：

| 关键字 | 作用 |
|---|---|
| `化(值)` | JSON 序列化 |
| `化(值, "缩进")` | 带缩进的美化输出，适合人工审查与 diff |
| `解(文本)` | JSON 反序列化，得到字典 / 数组 |

实测记录（2026-11-18，玄铁 1.0-rc，macOS arm64，`xtl pao` 直接运行）：

| 能力 | 结果 |
|---|---|
| 中文键原样保留 | ✅ 输出 `{"所属幕": "幕三"}`，不转义成 `\uXXXX` |
| 嵌套字典 / 数组，任意深度 | ✅ 往返一致 |
| 布尔 / 整数 / null | ✅ |
| 缩进输出 | ✅ 2 空格缩进，可直接给人看 |
| 引号 / 换行 / 斜杠转义 | ✅ |
| **浮点数** | ❌ `化(3.14)` 得到 `"object"`；`解("0.1")` 得到 `0`。更隐蔽的是嵌套：`化({"坐标": 3.14})` 得到 `{"坐标": "object"}`——**仍是合法 JSON**，合法性校验挡不住 |
| **指数记法** | ❌ `解("1e3")` 得到 `1`，量级错 1000 倍（源码用 `atoll` 截断，小数点与 e/E 都被丢弃） |
| 自定义类型（`型` 实例） | ⚠️ 实例**运行时就是字典**——编译器把 `__类型__`、字段、**全部方法（含构造器）**一起塞进同一个字典，序列化走普通字典分支，函数值与浮点共用同一个 `"object"` 兜底；`解()` 回读为字典、**不重建实例** |
| 非法 JSON / 空串 / `null` | ⚠️ 全部解析成 `空`，三者无法区分 |
| 字典键序 | ⚠️ 由哈希决定，与书写顺序无关（`{"甲":1,"乙":2}` 与 `{"乙":2,"甲":1}` 输出逐字节相同），但同内容输出稳定 |
| **UTF-8 BOM 开头** | ❌ **两层都没处理**：`xt_json_deserialize` 不跳 `\xEF\xBB\xBF`、`文件.读` 也不剥，整份配置**静默变成 `空`**，无报错。Windows 记事本「另存为 UTF-8」默认带 BOM，玩家改一次就可能把整章剧情读成空 |
| **≥ 2^62 的大整数** | ❌ 根因是装箱宏：`#define XT_FROM_INT(i) (((XTValue)(i) << 1) \| XT_TAG_INT)`（`runtime/xt_runtime.h:78`）——整数按「值左移 1 位 + 1 位类型标签」存，**上限只有 ±(2^62-1)**，≥2^62 左移即溢进符号位。`2^62`→`-2^62`、`2^63-1`→`-1`、`2^62+1`→`-(2^62-1)`；字面量 / `化()` / `解()` 三路一致，因为都过这个宏。**且传染运算与比较**：`大/2` 为负、`大 > 2^61` 为假 |

由此推出六条硬规则，写代码时必须守：

1. **配置里禁止出现小数。** 时间、坐标、系数一律整数——分钟用整数分钟，
   比例用千分制整数（如 `节奏千分比: 1250`）。
   这条直接影响第 7 节：节奏对数与离散本身是浮点，只能活在运行态内存里，
   若将来要落成 JSON 存档，必须先转成整数标度。
2. **剧情数据只用字典和数组表达，不用自定义类型。** `型` 实例运行时本就是字典，
   方法（含构造器）会一并序列化成 `"object"`，回读只得字典、不重建实例。
   待上游 #148 定契约后才考虑放宽到「纯字段型实例」，**当前不放宽**。
3. **配置里不要写 `1e3` 这类指数记法。** 反序列化用 `atoll` 截断，`1e3` 会变成 `1`，
   静默错三个数量级。整数请写全 `1000`。
4. **引擎只读配置，永不回写剧情文件。** 键序既然由哈希决定、与书写顺序无关，
   那么只要引擎不写回，文件就永远保持作者手写的字段顺序，diff 干净可读；
   一旦引擎回写，字段顺序会被打乱成哈希序。
5. **剧情 JSON 文件一律存成 UTF-8 无 BOM。** 带 BOM 会被 `解()` 静默读成空。
   校验脚本必须加一条：读文件时前三个字节是 `EF BB BF` 就报错，并提示「请存为无 BOM 的 UTF-8」。
6. **数值不得超过 2^62-1（4,611,686,018,427,387,903）。** 注意这不是 int64 的 2^63 上限，
   而是玄铁自己的**装箱上限**：整数按 `值<<1 | 1位标签` 存，左移吃掉一位，所以只剩 62 位。
   超过即静默变负数，而且**运算与比较一起坏**（不只是序列化）。校验脚本挡一道，别等它坏。

**注：自举分歧（上游 #148 已记录）**
Go 引导编译器在实例化时跳过构造器（`compiler/llvm.go:1734`，`if methodName == "造" { continue }`），
自举后的 XTC 编译器不跳过，因此分发包产物连 `造` 都被写进实例字典、再被序列化。
两个编译器行为不一致，`造` 到底该不该进字典，由作者定。

**注：构造期静默失败（上游拟另立 #149，与 #148 分层）**
没有构造器的型，`造 X(1, 2)` 的实参被**整个跳过、不编译、不报错**，字段停在默认值。
上游源码定位：XTC `编译实例化`（`xuantie_compiler/编译.xt:2724` 起）只有定义了构造器才处理实参
并校验个数（个数不符编译期报错）；「未定义构造器」分支整体跳过。Go 引导编译器同病，修复需两处同步。
这是**构造期**缺陷，#148 是**序列化语义**，故另立单，不并入。

**注：`__类型__` 魔术键（作为 #148 追评提交）**
本项目配置由玩家手改，`__类型__` 一旦成为自动重建的开关，玩家手写同名键就会被误判成实例。
请上游在契约里二选一定死：① `__类型__` 是保留键、位置固定；② 改用命名空间前缀（如 `__玄铁_类型__`）；
并明确 `解()` 遇到未知 `__类型__` 时是忽略、报错还是原样留在字典里。

**工具链层次**：日常一律走 `xtl`（Rust 写的驱动，`xinjian` / `pao` / `jiancha` / `qingli`），
由它内部调用 `xtc`；编译器本体是自举链产物 XTC，不是 Go 引导的 GSC（二者行为不完全一致）。
唯一直接碰底层的是渲染程序的链接阶段：渲染包 raylib 是 Windows 构建，`xtc tie` 必然失败，
故由 `scripts/xtc-抓IR.sh` 截获 IR、再交给 clang 手动链接。

修复结论出来前，上面六条硬规则继续生效。

JSON 标准语法不支持注释，所以：

- **用 `说明` 字段承载注释**（仍是标准 JSON，任何解析器都能读）——采用这个；
- 不用 JSON5 / JSONC：玄铁内置的 `解()` 只认标准 JSON，改格式反而要自己写解析器。

### 9.3 不设防是设计选择，不是疏忽

不加密、不混淆、不加校验和。解谜的乐趣来自"想通"，不是"藏住"。
看到答案等于自己主动放弃一次乐趣，这个选择权交给玩家——配置里写一句 `说明` 提示即可，
不做任何技术阻挡：

```json
{ "说明": "本文件是幕三的全部剧情节点。如果你想自己解谜，先别往下看。" }
```

明文还有正面价值：卡死一小时之后的挫败，远大于"看了答案"的损失。
RPG Maker 时代的项目本来就是明文，玩家社区自发形成了"看之前先问"的默契。

### 9.4 只护反转与隐藏结局：更深一层目录

- 常规场景：`剧情/幕01.json`，就放在明面上；
- 反转与隐藏结局：`剧情/隐藏/`，**再深一层**，文件名本身也看不出内容；
- 玩家想看就自己再下钻一层目录去拿；不想被剧透就不进去。
  **这个选择权完全在玩家手上，不需要任何技术阻挡**；
- 配置里对应 `剧透级别=模糊`，游戏内图谱对这类节点默认不铺开。

### 9.5 一个幕一个文件

```text
剧情/
  幕01.json  幕02.json  ...  幕07.json
  隐藏/
    幕08-真结局.json
```

- **文件名用两位数字前缀**（`幕01`…`幕07`），保证文件管理器按名字排序天然正确；
  中文幕名可跟在后面（`幕03-对立面.json`），只作展示；
- 玩家在文件管理器里一眼看到叙事骨架，与游戏内事件树是同一份信息、不同形态；
- 一文件一幕：diff 干净，agent 改一幕不碰其他幕；
- 每个文件头部用 `说明` 字段写幕元数据（序号、入口场景、收束场景、类型先验分钟）。

### 9.6 这份明文数据让 agent 能做四件事

1. **校验**：前驱/后继一致、无孤儿节点、无不可达分支、无死胡同
   （落成 `scripts/校验剧情.rvs`，纯结构检查，不需要人读全文）；
2. **生成**：按场景模板写，必填字段齐全、枚举值合法，产出能直接过校验；
3. **校准**：批量回填「作者基准分钟」——可人工估，也可从测试跑的真实耗时回填；
4. **分级提示**：读玩家当前场景，按需递进输出
   - 一级：方向性——"这一层还有没搜过的角落"
   - 二级：具体对象——"注意走廊尽头那幅画"
   - 三级：答案——直接说解法

玩家自己打开 JSON 文件，等价于自己跳到三级。两者并存不矛盾：**提示的分级由玩家自己选**。

### 9.7 为机器可校验加的硬约束

- **JSON 键名一律中文**（`所属幕`、`作者基准分钟`……），与玄铁源码命名风格一致；
- 键顺序固定；枚举值封闭（`类型` 只有五种、`剧透级别` 只有三种）；
- 必填：编号 / 所属幕 / 幕内序号 / 类型 / 前驱 / 后继 / 通行条件；
- 缺省允许：作者基准分钟 / 路径长度升 / 概括；
- **编号规则 `幕序号-场景序号`**（如 `3-2`），分支加字母后缀（`3-2a`）。
  这样文件名、节点编号、玩家口述三者一致，人和 agent 沟通不用翻译。

### 9.8 解释字段：给 agent 的意图外化，也是玩家的自救材料

每个解谜节点除了答案，还必须有「设计意图」字段，写明：

- 答案为什么是这个数（数字代表什么）；
- 线索埋在哪里、玩家应该按什么顺序发现；
- 这个谜题想让玩家体会什么，而不是单纯拦路。

这个字段首要读者是 **agent**：作者和 agent 协作时，必须把脑子里的意图外化成文字，
否则 agent 无法理解「这里为什么这样设计、这段剧情为什么这么编」，只能对着结果瞎猜。
**意图外化是协作的前提，不是可选的附加说明。**

对玩家同样成立：卡到百思不得其解时打开文件看一眼，看到的不只是答案，
还有作者当时的想法。这不算作弊，反而是一种体验——「原来他是这么想的」。
玩家也可以把这个文件交给 agent，让 agent 讲给他听。
**没有躲、没有藏，放在那里，谁都可以看**，这就是全部。
### 9.9 两个视图，同一份数据

- 游戏内：渲染后的图谱，按 `剧透级别` 与 `已发现` 状态过滤；
- 文件管理器里：JSON 全文，不过滤。

不是两套系统，是同一份数据的两种视图——所以永远不会不一致。这是不设防带来的额外收益：
**玩家在游戏里看到的树，和他打开 JSON 看到的，必然是同一棵树。**

## 10. 剧情优先于谜题：解谜不是进度门槛

### 10.1 观察到的真实情况

大量玩家（包括主播、实况 UP 主）在解谜节点上耗半小时到一小时仍无进展。
问题不是"难度太高"，而是**信息不足**——猜密码、猜物品摆放位置，只能穷举。
这类时间不是挑战，是纯折损：玩家不是在享受难度，是在猜作者的设计意图。

### 10.2 因此定三条硬约束

1. **每个解谜节点都必须存在绕行路径**——替代线索、可选择的其他解法，或直接"绕过但保留剧情"；
2. **剧情推进权高于谜题**：玩家可以一个谜题都不理解，仍然能读完全部剧情、走到结局；
3. **既不为难也不羞辱**：主手段是**改配置**（见 10.6），比专门做难度界面省事；
   如果游戏内再做跳过/提示，也不弹「你使用了提示」、不扣成就（除非玩家自选挑战模式）。

### 10.3 在事件树上的体现

- 解谜节点标记为「可选挑战」，不占用主线必经位置；
- 被绕过的节点显示为「已绕过」，**不是「失败」，也不是「永久失效」**；
- 因此 `去向` 枚举必须把 **绕过** 与 **失败** 分开：
  失败 = 可选挑战没完成；绕过 = 主线照常推进。两者在树上颜色不同。

### 10.4 恐怖氛围的取向

恐怖靠叙事、压迫感、空间感建立，不依赖突然惊吓。所以：

- **惊吓预算压低**，jump scare 只作极少量点缀，不作为主要手段；
- 恐怖节点的成本主要在"读"和"走"，不在"被吓"——这也让剩余时间预估更稳、方差更小；
- 对只看剧情、不喜欢突然惊吓的玩家，这条直接决定他们能不能玩下去。

### 10.5 看客型玩家

有一类玩家（看主播实况、只读剧情、不亲自解谜、不喜欢突然惊吓）本就不是为解谜来的。
10.2 的三条对他们是刚需：他们要的是**剧情完整可达**，谜题只是观看时的调剂。
### 10.6 明文可改，本身就是难度调节

剧情是 JSON、答案是明文字段，那么**玩家能直接改答案**：

```json
{ "编号": "3-2", "类型": "解谜", "答案": "0000", "设计意图": "…" }
```

- 只想通关、又记不住那串数字的玩家，把答案改成 `0000` 就过去了，超级宽松；
- 不需要专门做「简单/困难」难度选项界面，**配置文件本身就是难度旋钮**；
- 不做校验和、不做防改检测——改了照样能跑。

先例：《心跳文学部》是 Ren'Py 的 `.rpy` 明文，玩家真去改过脚本、改过角色文件。
这类游戏的玩家生态里，「打开文件改」是常态而不是漏洞。

**额外机会（可选，不强推）**：既然文件可改，可以把「玩家改文件」这件事本身当成叙事的一部分。
DDLC 的 meta 恐怖正是建立在玩家能碰这些文件之上。若将来想做这一层，
必须先定清楚边界，否则会变成惩罚改文件的玩家。

### 10.7 谜题答案必须有内在逻辑

随机串密码 = 纯穷举 = 折磨。所以：

- 答案应当**可解释**：日期、门牌号、人数、谐音、某句台词里的字数……都行；
- 这条直接决定「设计意图」字段有没有东西可写——**作者先想清楚含义，才写得出来**；
- 玩家看了解释会觉得合理，而不是觉得作者想整他。

所以「解释字段」不是给谜题打的补丁，而是设计过程本身的产物。


## 11. 键位绑定（待设计）

本章只落「方向与已知约束」——具体键位尚未设计，先定接口形状，键位留给玩家。

### 11.1 现状：没有绑定层

`更新游玩()` 里全是硬编码键码：

```text
R.键按下?(87)   // W        R.键按下?(265)  // ↑
R.键按下?(83)   // S        R.键按下?(264)  // ↓
R.键按下?(65)   // A        R.键按下?(263)  // ←
R.键按下?(68)   // D        R.键按下?(262)  // →
```

改任何一个键都要改源码，再走「xtc 抓 IR + clang 手动链接」这条最重的构建链。
键位是玩家最想改的东西，却是最改不动的部分——与第 9 节「配置驱动」直接矛盾。

### 11.2 方向：动作名 → 键名列表

配置放 `配置/键位.json`，玩家自己改，不用重编译：

```json
{
  "说明": "改键不用重编译，改这里即可",
  "动作": {
    "上":     ["W", "上箭头"],
    "交互":   ["F"],
    "潜行":   ["C"],
    "冲刺":   ["双击上"],
    "手电筒": ["大写锁定"],
    "暂停":   ["ESC"]
  }
}
```

- 写**中文键名**，不写键码数字（键名给人看，键码给引擎用）；
- 一个动作可绑多个键（数组），天然支持「W 与方向键都能前进」；
- 引擎内置 键名 → 键码 表；配置里出现表外的名字，**启动时报错**，不许静默回落。

### 11.3 硬原则：不假设玩家手在 WASD 上

打字基准位的手（小指在 A）够不到 shift / control——那两个键在 A 的更左边，
小指的本职是够 A 和 Q，不是继续往左伸。所以：

**左侧修饰键不得作为默认功能键。** 功能键落在食指 / 中指可达区（E、R、F、C、V、X）。

这不是口味偏好，是键盘几何决定的结构性事实：越依赖左侧修饰键，
越把「打字基准位」的玩家排除在外。

### 11.4 caps lock 的四条未知（必须实机验证）

1. raylib 有 `KEY_CAPS_LOCK = 280`，但渲染库导出的中文常量表**没有** `键大写锁定`，
   要用只能裸写数字 280（不符合项目的中文常量习惯）；
2. caps lock 是**修饰键**，事件语义是「锁定状态翻转」而非可靠的按住 / 松开：
   **适合切换式**功能（手电筒开关、跑步模式锁），**不适合按住式**冲刺；
3. macOS 默认把它用于切换输入法，需在「系统设置 > 键盘 > 文本输入 > 输入法」
   取消「使用大写锁定键切换 'ABC' 输入法」才能让游戏拿到——属全局改动，代价是换输入法快捷键；
4. 以上三条均为**技术推断，未实测**。验证手段：加一个诊断屏，
   实时显示 `取按键()` 的返回值与 `键按下?(280)` 的状态，按一遍 caps lock 看事件是否成对。

### 11.5 待定项（本轮不定）

- 具体键位表（交互 F、潜行 C 只是倾向，未拍板）；
- 冲刺到底绑键，还是用「双击前进」/「按住前进 0.4 秒自动加速」——后者不占任何手指，
  且与 Minecraft 肌肉记忆一致；
- 冲突检测（同一个键绑到两个动作）放进哪个校验脚本；
- 重绑 UI 是否需要：用 `取按键()`（队列式，0 = 无新键）实现「请按下新键」的捕获；
- 重绑结果是否写回文件——写回会打乱键序（见 9.2 第 4 条），倾向**不写回**，只做会话内生效。

## 12. 布局与渲染约束

- L0：主轴水平居中，幕等距排列；未知幕只占位不写名；主轴始终直。
- L1：主线横排，分支向上下两翼展开，深度限制 1 层（可展开到 2 层但需玩家手动）。
- 任何时刻分支宽度 ≤ 3；超出则折叠远端，深度默认 1 层。
- 已经完成且不影响后续预测的幕，允许"收起为标记"，保留一键展开。

## 13. 与现有引擎的对接

- 现有事件系统只需补 所属幕 / 幕内序号 / 类型 / 作者基准分钟 / 剧透级别 五个字段；
- 前驱 / 后继 若已有事件跳转表，可直接从跳转关系推导，不必手写；
- 运行态（已发现 / 状态 / 采样 / 节奏对数 / 离散）全部走现有存档，不进设计数据；
- 渲染层独立于游戏主循环，只在打开视图时读取快照，避免每帧轮询。

## 14. 落地顺序（建议）

1. **配置层**：剧情按幕拆成 `剧情/幕N.json`，引擎侧只加一个加载器；
   同时写 `校验剧情.rvs`（无 UI，能过校验就算验收）；
2. **L0 幕视图**：只画幕序列 + 已完成/当前/未知三态，硬编码 7 幕验证观感；
3. **L1 场景视图**：当前幕展开，主线 + 挂载点，分支宽度限 3；
4. **采样与预估**：先采 `a_i`（含解谜/跑图/阅读全部计入，只剔第三类），
   再算实测步速与移动下限，最后上节奏对数与两档文案；
5. **剧透控制与未知幕预渲染**：最后加，因为它们影响的是体验细节而非结构。

## 15. 原型验证：第一幕已经跑通（2026-11-18）

纸面写到第 14 节，但一行代码都没验证过。补一个**纯文本原型**——不接渲染，用 `示` / `输` 直接跑：

- `剧情/幕01.json`：第一幕 8 个节点（必经 / 谜题 / 绕过 / 分支 / 两个结局）
- `原型/剧情播放器.xt`：读 JSON → 逐节点播放 → 记录每节点耗时
- 编译运行：`xtc tie 原型/剧情播放器.xt -sc 播放器`，在项目根 `./播放器`

为什么不先接渲染：渲染壳每次构建都要走「抓 IR + clang 手动链接」，改一行要等很久；
纯文本是 `xtl pao` 秒级。**先用最便宜的壳验证结构，再套最贵的壳。**

### 15.1 跑通的三条路径

| 路径 | 节点序列 | 是否正常终止 |
|---|---|---|
| 知情（密码对 + 左转） | 1-1 → 1-2 → 1-4 → 1-5 → 1-7 | ✅ |
| 绕过（密码错 + 撬门） | 1-1 → 1-2 → 1-3 → 1-4 → 1-5 → 1-7 | ✅ |
| 错过（密码对 + 下楼） | 1-1 → 1-2 → 1-4 → 1-6 → 1-8 | ✅ |

### 15.2 验证了什么

- **字段够用**：`标题` / `正文` / `设计意图` / `剧透级别` / `作者基准分钟` / `后继` / `选项` / `谜题`；
- **谜题与绕过能表达**：`谜题.对` 与 `谜题.错` 是两条出边，错的通向绕过节点，绕过节点再接回主线；
- **分支只改「知道多少」**：左转读到登记册（解释密码），右转直接下楼（错过解释），主线不受影响；
- **结局 = 无 `后继` 的节点**，不需要额外的终止标记。

### 15.3 撞到的三个语法坑

1. **`选` 是关键字**，不能作变量名（`设 选 = …` 直接编译失败），改用 `选项表`。
2. **嵌套 `否` 会被当成同层多个 `否`**（触发 W004，只有第一个生效）。
   分支判断要拍平成并列的 `若 … 若 …`，不要 `若 { 若 { } 否 { } } 否 { }`。
3. **缺失键赋给字符串变量会变成字符串「空」**：结局节点没有 `后继`，
   `设 后 = 节点["后继"]` 取到 `空`（null），而 `后 != ""` 仍为真，于是去查 `事件["空"]`。
   **任何可选字段使用前必须显式判 `空`**，不能指望它等于空串。

### 15.5 第一次真实样本（作者自测，只能当下限）

2026-11-18，作者本人跑了一遍「密码对 + 下楼」：

| 节点 | 字数 | 实际耗时 | 阅读速度 | 作者基准 |
|---|---|---|---|---|
| 1-1 铁门 | 67 | 28.4 秒 | 2.4 字/秒 | 2 分 |
| 1-2 转盘锁 | 41 | 7.5 秒 | 5.5 字/秒 | 5 分 |
| 1-4 分岔 | 45 | 12.4 秒 | 3.6 字/秒 | 2 分 |
| 1-6 楼梯 | 36 | 3.7 秒 | 9.8 字/秒 | 2 分 |
| 1-8 结局 | 约 30 | 未测（旧版结局无回车） | — | 1 分 |

**这组数不能当平均，只能当下限**，三个理由：

1. 作者知道答案（`0421` 是自己写的），1-2 只花 7.5 秒不是谜题容易，而是根本没在解；
2. 文本是他刚写的，基本是扫读，1-6 的 9.8 字/秒就是扫读速度；
3. 1-1 的 28 秒里有很大一块是「进入状态」的一次性成本，不该摊给每个节点。

**但三条结论可以直接采纳：**

- **阅读速度取下限 2~3 字/秒**（2.4 是本次最慢的一组，恐怖文本会比扫读更慢）；
- **谜题节点必须单独建模**，不能并入阅读速度——它是双峰的：知道答案 7 秒，不知道可能十分钟以上；
- **第一个节点单列「启动成本」**（约 20~30 秒，一次性，不参与节奏系数）。

对应到第 7 节的模型：纯阅读时间按 `字数 × 0.4 秒` 估算（约 2.5 字/秒），
移动时间仍用实测步速，解谜单独用对数正态，首节点加一次性启动。

**测量口径的修正**：结局节点原来没有输入，测到 `0 ms`——玩家读完不会按任何键。
现在结局也要「（回车结束）」，读到此处的时间才算得进去。

### 15.6 第一次「不知情」试玩（作者换成不知情身份）

换掉整条谜面后，作者以不知情玩家身份跑了一遍（答案猜错 → 撬门 → 下楼）：

| 节点 | 字数 | 耗时 | 速度 |
|---|---|---|---|
| 1-1 铁门 | 74 | 96.7 秒 | 0.8 字/秒 |
| 1-2 转盘锁 | 46 | 10.4 秒 | 4.4 字/秒 |
| 1-3 撬门 | 44 | 7.7 秒 | 5.7 字/秒 |
| 1-4 分岔 | 45 | 38.8 秒 | —（决策，不是阅读） |
| 1-6 楼梯 | 36 | 2.7 秒 | 13.3 字/秒 |
| 1-8 结局 | 30 | 11.7 秒 | 2.6 字/秒 |
| 合计 | 275 | 168 秒 | — |

**三条结论：**

1. **阅读速度区间极大（0.8 ~ 13 字/秒，差十几倍）**，`字数 × 固定速度` 不可能准。
   必须用玩家自己的历史中位数滚动校准——第 7 节原本就是这么设计的，这次数据反过来证明了它。
   （1-1 的 96 秒里还混着「一边读对话一边读游戏」的外部干扰，不是纯游戏时间。）
2. **选择节点必须单独计时**：1-4 只有 45 字，却用了 38.8 秒——是在犹豫走哪边。
   决策成本和谜题一样，不能并入阅读速度。
3. **谜题只猜一次就放弃（10.4 秒）**：因为原设计是「错一次即强制绕过」，玩家没有第二次机会。
   这暴露了一个体验问题：谜题几乎没起作用就被跳过，玩家也没机会试第二次。
   已改为：答错后由玩家自己决定「再试一次」还是「撬门」，并记录试答次数。

### 15.7 终端意外验证了一件事：**文本必须能回头读**

这次试玩里，玩家在结局节点做了终端才允许做的事：**往上滚，重读前面的正文**，
把结局和前面的线索放在一起对照。

这正是 2D 的 RPG Maker 恐怖游戏通常做不到的——对话框消失就是没了。
galgame 之所以能做，是因为它有 back-log（历史记录）。

**由此定一条约束：必须提供已读文本回顾。** 否则玩家的「原来如此」时刻会被结构性剥夺，
只剩「看不懂」——而第 10 节已经说过，看不懂的谜题没有乐趣。

对照我们自己的设计：事件树视图里每个已走过的节点，都应该能展开重读原文，
这既是「我走过哪儿」的地图，也顺带就是 back-log。

**回顾要覆盖三类文本，不是只有对话：**

1. **对话**——角色说的，按键过快时最容易漏；
2. **旁白**——叙述描写，线索多半藏在这一类里；
3. **系统提示**——「门锁着」「电筒电量不足」「存档完成」，一闪而过，
   玩家几乎不会主动回看，但它是理解规则的钥匙。

三类进同一个回滚缓冲、按发生顺序排列，**不要按类型分栏**：
玩家回想的是「刚才那一下」，不是「某一种文本」。

触发场景也不只是「想串联线索」：**按键太快漏读**是更常见的动机。
所以缓冲要在每次文本推进时无条件写入，不能等玩家「觉得需要」。
