# 事件树视图设计（叙事图谱 / Event Tree）

> 状态：设计稿（v0.1），尚未实现。本文档定义目标、交互形态、数据结构与时间预估模型，
> 供后续在玄铁版「无尽回廊」中分阶段落地。

## 1. 定位

给玩家一张**自己探索出来的**剧情结构视图，回答三个问题：

1. **我在哪？** 当前节点在整个叙事结构里的坐标。
2. **前面还有什么？** 还有多少可探索的通路、还剩多长。
3. **哪些已经永久错过？** 避免"回头重开"的挫败。

它**不是**完整剧情剧透，也不是逐句台词预览。展示的是玩家已探测到的部分，而非设计师原图。

## 2. 核心判断：大节点不是"节点"，是"刻度"

玩家在大节点这一层想要的不是拓扑，而是**进度标量**（"我前面还有多久"）；
小节点承载的才是**选择**（"我有哪几条路"）。两者认知诉求不同，混在同一视图必然乱。

因此采用 **一维主轴 + 局部二维展开**（focus + context）：

```text
L0 幕视图（默认，永远只是一条横线）
  [幕一 ✓]──[幕二 ✓]──[幕三 ●]──[幕四 ◇]──[幕五 ?]──[≈?]
   ← 已体验 ───────────── 当前 ────── 未知（有界推测） ─→

L1 场景视图（点开「幕三」才出现）
                 ┌─ 场景3-2a ─┐
  场景3-1 ── 场景3-2 ── 场景3-3 ── 场景3-4（幕末）
                 └─ 场景3-2b ─┘
```

## 3. 三层颗粒度

| 层 | 单位 | 职责 | 何时可见 |
|---|---|---|---|
| **幕 Act** | 叙事大段落（建议 5~9 个） | 进度刻度、剩余量预估 | 永远可见，线性横排 |
| **场景 Scene** | 一段闭环剧情单元 | 选择与分支、**时间统计基本单位** | 仅所属幕展开时 |
| **节拍 Beat** | 单次选择、单条件判定 | 细节 | 默认隐藏，hover/详情面板 |

**硬规则：同一屏同时可见的分支宽度（breadth）≤ 3。**
每次展开只显示当前节点 ±1 层，绝不同时铺开整个子树。
乱不乱取决于同时可见的宽度，而非总节点数。

### 3.1 场景层的「主线 + 挂载点」

幕内不要真做成树，做成：

- 一条**必然走过的场景序列**横排（场景3-1 → 3-2 → 3-3 → 幕末）；
- 分支是挂在某个场景**上方/下方**的子条，走完回归主线（回流型），或标记为脱离（分流型）；
- 走完后子条收拢成角标，不留在画面上。

即使幕内有 10 个场景、8 条分支，可见结构仍是「一条线 + 几个括号」。

## 4. 线性可行的前提：幕级分叉被强约束

L0 一旦出现三四个并列轨道，玩家无法把多条并行剩余量加成一个标量，预估立刻失效。故：

- **幕级分叉全流程最多 1~2 次，且必须是显式 Y 形分叉**（如"第一章末二选一"），
  分叉后各自再收束成一条线；
- 绝大多数选择只影响**幕内场景序列**，不影响幕的走向与数量；
- 玩家无论怎么选，都会推进到下一个幕。

副作用（正面）：幕视图的线性直接定义了"叙事总量"——看到 7 个格子即知是 7 幕规模。

### 4.1 幕边界必须人工标记，不自动聚类

自动聚类会让边界随事件增删漂移，玩家上次记住的"幕三"变成"幕四"，记忆错位。
幕边界是设计资产：每个事件只加 `act_id` + `act_order` 两个字段，幕视图纯靠它们渲染。

## 5. 节点状态与视觉语义

| 状态 | 视觉 | 含义 |
|---|---|---|
| 已完成 | 绿色实框 | 已走完 |
| 已发现未进入 | 浅灰实框 | 玩家知道存在，未触发 |
| 已知存在但未知内容 | 半透明虚框 | 推测/暗示，未确认 |
| 当前 | 高亮描边 | 玩家所在节点 |
| 永久关闭 | 暗红/暗灰，连线枯萎 | 错过、失败、分支已封死 |

- **连线**：一条线 = 一条可行通路，可附极简条件标记（选择 A / 物品持有 / 好感达标 / 时间窗口）。
  条件未满足时显示"条件未知"，不显示具体条件文本。
- **折叠**：已完成的旧枝可收拢，只看前方，避免画面爆炸。
- **锚点标记**：允许玩家手动标记节点，便于回忆当时的选择。

## 6. 未知节点的渲染规则（防剧透边界）

- 未知节点**不能以实框出现**；
- 未知幕最多预渲染 **2 个**（紧邻的下一个 + 再下一个的轮廓）。再多，未知感被稀释，
  且布局会随剧情推进剧烈抖动；
- 预渲染用虚框 + 占位符号，**不写任何标题，不给未知幕编号**——编号会把未知变成清单/KPI，破坏悬念；
- 不提前暴露"这个选择通向哪个结局"；
- 关键反转节点：即使前置满足，也等到触发后才补全节点与连线；
- 隐藏结局节点描述保持模糊，保留悬念。

## 7. 时间预估模型（滚动 ETA）

### 7.1 结论先行

**节点不标注"预计几分钟"，改为按玩家自己的节奏预测。**
作者手填的时长对单个玩家无效：同一段剧情的耗时方差极大（跳过文本 vs 穷举角落），
跨玩家平均对谁都不准。唯一有意义的是"这个玩家前几个节点的实际速度"。

两个输入：
- `e_i`：**作者基线**（场景级），仅作冷启动先验与归一化基准；
- `a_i`：**玩家实际有效耗时**，主信号。

### 7.2 有效耗时采样

```
enter_scene(i) -> t0
exit_scene(i)  -> t1
raw = t1 - t0
```

必须剔除"挂机"：恐怖 RPG 读文本、被吓住、离开座位都会让墙钟时间失真。

```text
idle_gap = 相邻两次玩家输入/事件触发之间的最大间隔
if idle_gap > IDLE_THRESHOLD (建议 120s): 该段从 raw 中扣除
a_i = clamp(raw, e_i * 0.3, e_i * 3.0)     # 上下截尾，防一次看攻略 2 小时拉爆样本
```

### 7.3 个人节奏系数

```text
r = weighted_median( a_i / e_i )  over 最近 K 个已完成场景（K = 5~8，近期加权）
```

- 样本数 `n < 3`：不做点估计，只给区间 `[0.6r, 1.6r]`，或直接说"约十几分钟"；
- 多周目：优先用最近一周目样本；跨存档样本可聚合但设上限，避免旧习惯污染；
- 玩家节奏变化（开始认真读文本 / 开始速通）：`K` 窗口保证系数自然跟随。

### 7.4 剩余时间预测

```text
剩余预测 = Σ_{j ∈ 已发现未走的场景} r * e_j
         + Σ_{幕 ∈ 未知幕} r * act_prior(该幕类型)
```

- **场景是统计与预测的基本单位**，向上汇总到幕、再汇总到全流程；
- 未手工填 `e` 的节点用**类型先验**（对话 / 探索 / 战斗 三类各自的历史均值），
  减少作者手填工作量；
- 粒度权衡：幕级太粗（误差被摊平、分辨率低），节拍级太细（噪声大），**场景级最稳**。

### 7.5 UI 表达

- 幕视图：当前幕下方标「进行中 · 已 12 分钟」，已完成幕标实际耗时；
- 全局：角落小字「按当前节奏，还需约 X 分钟」（带区间）；
- **不要**用"还有 3 个节点"这种引擎内部计数替代时间——玩家对齐的是时间成本，不是事件数量。

## 8. 数据结构草案

```text
Scene = {
  id:           唯一标识
  act_id:       所属幕（人工标记）
  act_order:    幕内序号
  kind:         对话 | 探索 | 战斗 | 过场
  title:        摘要标题（L1 展示用，非台词）
  summary:      一句话概括
  parents:      [Scene.id]      # 哪些场景能到达它
  successors:   [Scene.id]      # 它的出口
  gate:         { choices: [...], items: [...], flags: [...], time_window: ? }
  divergence:   回流 | 分流
  author_minute: 作者基线 e（可缺省 -> 用 kind 先验）
  spoil_level:  正常 | 延迟揭示 | 模糊      # 剧透控制开关
}

Act = {
  id, order, title_known: bool,   # 未知幕 title_known = false
  entry_scene, terminal_scene
}

RuntimeState（存档内，不随设计变更）:
  discovered: set<Scene.id>
  status:     map<Scene.id, 未发现|已发现|进行中|已完成|永久失效>
  samples:    map<Scene.id, {raw, effective, count}>
  pace_ratio: r
```

## 9. 布局与渲染约束

- L0：主轴水平居中，幕等距排列；未知幕只占位不写名；主轴始终直。
- L1：主线横排，分支向上下两翼展开，深度限制 1 层（可展开到 2 层但需玩家手动）。
- 任何时刻 breadth ≤ 3；超出则折叠远端。
- 已经完成且不影响后续预测的幕，允许"收起为标记"，保留一键展开。

## 10. 与现有引擎的对接

- 现有事件系统只需补 `act_id` / `act_order` / `kind` / `author_minute` / `spoil_level`；
- `parents` / `successors` 若已有事件跳转表，可直接从跳转关系推导，不必手写；
- 运行态（发现/状态/采样/节奏系数）全部走现有存档，属于 runtime state，不进设计数据；
- 渲染层独立于游戏主循环，只在打开视图时读取快照，避免每帧轮询。

## 11. 落地顺序（建议）

1. **数据层**：事件结构补字段 + 从跳转表推导 parents/successors（无 UI，先能 dump 出结构）；
2. **L0 幕视图**：只画幕序列 + 已完成/当前/未知三态，硬编码 7 幕验证观感；
3. **L1 场景视图**：当前幕展开，主线 + 挂载点，breadth 限 3；
4. **采样与 ETA**：先采 `a_i` 与去挂机，再上 `r`，最后接 UI 文案；
5. **剧透控制与未知幕预渲染**：最后加，因为它们影响的是体验细节而非结构。

## 12. 待决问题

- 未知幕预渲染 2 个是否偏多？恐怖题材或许 1 个更压抑（需实测）。
- `IDLE_THRESHOLD` 与 `K` 的取值需靠真实玩家数据校准，当前只是经验值。
- 分叉后"永久失效"的枝，是立即枯萎还是延迟到幕末再变暗（延迟能给玩家反悔感）。
- 是否需要"上周目树叠加"（多周目补全整棵树）——会显著提升完成欲，但也会泄露上周目未走的分支。
