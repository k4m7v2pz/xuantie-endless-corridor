# 随机数与种子：系统熵、引擎随机、存档可复现

> 一句话：**熵是"不可预测的输入"，种子是"可复现的起点"，两者不能混用。**

## 1. 操作系统那边（macOS / Unix）

- 名词是**熵（entropy）**，不是"商"。内核维护一个**熵池**，来源：
  硬件真随机（Apple 芯片片上有 TRNG，Secure Enclave 也供货）、启动时的时序抖动、
  中断到达时间的抖动（键鼠、磁盘、网卡）。键鼠输入历史上是熵源之一，
  **现在只占很小一份**，主力是硬件 RNG。
- 对外接口：`/dev/random` 与 `/dev/urandom`（macOS 上同一条 CSPRNG 流，启动后不阻塞）、
  `getentropy(2)`、`arc4random_buf()`。拿到的是**已混洗的随机字节**，
  不是"原始熵"本身，也**读不出种子**——设计上就不让上层反推。
- 所以"系统按键盘输入攒种子"这个印象来自早期 Unix/Linux 的熵池采集，
  机制还在，但今天的随机性主要不是靠你敲键盘。

## 2. 玄铁这边（实测）

- `数学.随机(上限)` / `数学.随机小数()` / `R.取随机数` 底层都是 C 的 `rand()`。
- `数学.设随机种子(种子)` 就是 `srand()`。
- **坑**：不调 `设随机种子` 时 `rand()` 用的是默认种子，
  每次启动得到**完全相同的序列**。所以"开局随机"必须先设种子：

```text
数学.设随机种子(时.现())
```

- 反过来，要用随机但**可复现**的东西（每日挑战、固定剧情随机、复现 bug），
  就把种子当成数据存起来：`设随机种子(存档里的种子)`，而不是每次现取。

## 3. 存档与随机的关系（本作口径）

- **存档标识**（7 位十六进制）现在走的是确定性混洗（现实秒 + 已玩毫秒 + 玩家格），
  不需要系统熵，也不需要随机数——同一时刻同一状态必然同号，便于排查。
- **玩法随机**（怪物出现位置、掉落、闪现时机）建议在存档里多存一个 `随机种子` 字段：
  读档后从同一个种子续跑，录像复盘与玩家反馈才能对上。
  这字段还没进 `saves/*.json`，接玩法随机时一起加。
- **不要**把系统熵当"随机感"来源：它不可复现，出了问题谁也没法重放。

## 4. 恐怖游戏的随机事件：别让玩家靠按方向键改随机

老 RPG（RPG Maker 那一类）里常见一种土办法：随机数跟着**帧数/输入**推进，
玩家想改结果就原地狂按方向键、来回蹭两步"刷随机"；被鬼抓了读档，重走一遍同样的路
往往还是同一个结果，只能靠更多余的动作去扰动。这不是玩家迷信，是随机源挂错了地方。

引擎该给创作者的东西：**一个与帧、按键、鼠标位置无关的随机入口**。

- 事件判定点固定在剧情节点上（"进这间屋第 3 步触发一次鬼"），
  点一到就取一次系统熵，按键多少、站多久、镜头在哪都不影响结果。
- 玩家不用做任何"仪式性操作"，读档回来也不会因为手速不同而命运不同。
- 创作者不需要懂随机数理论，写剧情时只要说"这里有一次 30% 的遭遇"。

取法对比（为什么非要系统熵）：

| 取法 | 可复现 | 玩家能干预吗 | 适合 |
|---|---|---|---|
| `数学.随机`（底层 `rand()`） | 设种子后可以 | 能（跟着帧/输入推进，可刷） | 纯表现层抖动（粒子、闪烁间隔） |
| 时间戳当种子（`时.现()`） | 秒级可猜 | 能（卡时间点） | 每日挑战、按天固定的内容 |
| 系统熵（`/dev/urandom`、`getentropy`） | 不能（这是目的） | **不能** | 遭遇判定、掉落、惊吓时机 |

### 玄铁这边缺什么（实测）

GUIDE 与 lib 目录里翻遍了，只有 `数学.随机` / `数学.随机小数` / `R.取随机数`，
**没有系统熵入口**（没有 `getentropy` / `getrandom` / `BCryptGenRandom` 的封装）。
所以现在只能用壳层命令兜底，例如 macOS/Linux：

```text
设 熵字 = 执("od -An -tu4 -N4 /dev/urandom")
```

一次 syscall 量级是微秒，事件级（几秒一次）完全够；但它是字符串、要解析，
而且 Windows 上没有 `od`，得换 `powershell` 取 `BCryptGenRandom`，跨平台不好写。

建议给上游提的接口（名字随意，形态是"字节级、可指定个数"）：

- `系统.随机字节(个数)` → 返回字节；底层 macOS `getentropy`/`arc4random_buf`、
  Linux/Android `getrandom`、Windows `BCryptGenRandom`。
- 在此之上包一层 `系统.随机整数(上限)`，创作者直接用这个就够了。

### 顺带纠正一个印象

**Windows 也有熵池**，只是没有 `/dev/random` 这种文件形态：
`BCryptGenRandom` / `RtlGenRandom` 背后同样是系统 CSPRNG，硬件 RNG + 时序抖动供货。
所以"除了 Windows 都有"不成立——真正缺的是**玄铁这一层没做封装**，不是平台没有。

### 不可预测 ≠ 不能复盘

两条要同时满足：事前不可预测、事后可查。做法是"**判定即落档**"：

- 事件触发的那一刻取熵、算出结果，然后把这个结果（连同当时的种子/序号）写进存档与日志。
- 读档回来按存档里的结果走，不会重抽；玩家想刷也刷不动，开发者拿到日志却能复盘。
- 若允许"读档重抽"，那是设计选择（Roguelike 常见），要在文档里写明，别让它变成隐藏漏洞。
