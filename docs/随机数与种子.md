# 随机数与种子：系统熵、引擎随机、存档可复现

> 一句话：**熵是"不可预测的输入"，种子是"可复现的起点"，两者不能混用。**

## 1. 操作系统那边（macOS / Unix）

- 名词是**熵（entropy）**，不是"商"。内核维护一个**熵池**，来源：
  硬件真随机（Apple 芯片片上有 TRNG，Secure Enclave 也供货）、启动时的时序抖动、
  中断到达时间的抖动（键鼠、磁盘、网卡）。键鼠输入历史上是熵源之一，
  **现在只占很小一份**，主力是硬件 RNG。
- 对外接口：`/dev/random` 与 `/dev/urandom`（macOS 上同一条 CSPRNG 流，启动后不阻塞）、
  `getentropy(2)`、`arc4random_buf()`。拿到的是**已混洗的随机字节**，
  不是"原始熵"本身，也**读不出种子**——设计上就不让上层反推。
- 所以"系统按键盘输入攒种子"这个印象来自早期 Unix/Linux 的熵池采集，
  机制还在，但今天的随机性主要不是靠你敲键盘。

## 2. 玄铁这边（实测）

- `数学.随机(上限)` / `数学.随机小数()` / `R.取随机数` 底层都是 C 的 `rand()`。
- `数学.设随机种子(种子)` 就是 `srand()`。
- **坑**：不调 `设随机种子` 时 `rand()` 用的是默认种子，
  每次启动得到**完全相同的序列**。所以"开局随机"必须先设种子：

```text
数学.设随机种子(时.现())
```

- 反过来，要用随机但**可复现**的东西（每日挑战、固定剧情随机、复现 bug），
  就把种子当成数据存起来：`设随机种子(存档里的种子)`，而不是每次现取。

## 3. 存档与随机的关系（本作口径）

- **存档标识**（7 位十六进制）现在走的是确定性混洗（现实秒 + 已玩毫秒 + 玩家格），
  不需要系统熵，也不需要随机数——同一时刻同一状态必然同号，便于排查。
- **玩法随机**（怪物出现位置、掉落、闪现时机）建议在存档里多存一个 `随机种子` 字段：
  读档后从同一个种子续跑，录像复盘与玩家反馈才能对上。
  这字段还没进 `saves/*.json`，接玩法随机时一起加。
- **不要**把系统熵当"随机感"来源：它不可复现，出了问题谁也没法重放。

## 4. 恐怖游戏的随机事件：别让玩家靠按方向键改随机

老 RPG（RPG Maker 那一类）里常见一种土办法：随机数跟着**帧数/输入**推进，
玩家想改结果就原地狂按方向键、来回蹭两步"刷随机"；被鬼抓了读档，重走一遍同样的路
往往还是同一个结果，只能靠更多余的动作去扰动。这不是玩家迷信，是随机源挂错了地方。

引擎该给创作者的东西：**一个与帧、按键、鼠标位置无关的随机入口**。

- 事件判定点固定在剧情节点上（"进这间屋第 3 步触发一次鬼"），
  点一到就取一次系统熵，按键多少、站多久、镜头在哪都不影响结果。
- 玩家不用做任何"仪式性操作"，读档回来也不会因为手速不同而命运不同。
- 创作者不需要懂随机数理论，写剧情时只要说"这里有一次 30% 的遭遇"。

取法对比（为什么非要系统熵）：

| 取法 | 可复现 | 玩家能干预吗 | 适合 |
|---|---|---|---|
| `数学.随机`（底层 `rand()`） | 设种子后可以 | 能（跟着帧/输入推进，可刷） | 纯表现层抖动（粒子、闪烁间隔） |
| 时间戳当种子（`时.现()`） | 秒级可猜 | 能（卡时间点） | 每日挑战、按天固定的内容 |
| 系统熵（`/dev/urandom`、`getentropy`） | 不能（这是目的） | **不能** | 遭遇判定、掉落、惊吓时机 |

### 玄铁这边缺什么（实测）

GUIDE 与 lib 目录里翻遍了，只有 `数学.随机` / `数学.随机小数` / `R.取随机数`，
**没有系统熵入口**（没有 `getentropy` / `getrandom` / `BCryptGenRandom` 的封装）。
所以现在只能用壳层命令兜底，例如 macOS/Linux：

```text
设 熵字 = 执("od -An -tu4 -N4 /dev/urandom")
```

一次 syscall 量级是微秒，事件级（几秒一次）完全够；但它是字符串、要解析，
而且 Windows 上没有 `od`，得换 `powershell` 取 `BCryptGenRandom`，跨平台不好写。

建议给上游提的接口（名字随意，形态是"字节级、可指定个数"）：

- `系统.随机字节(个数)` → 返回字节；底层 macOS `getentropy`/`arc4random_buf`、
  Linux/Android `getrandom`、Windows `BCryptGenRandom`。
- 在此之上包一层 `系统.随机整数(上限)`，创作者直接用这个就够了。

### 顺带纠正一个印象

**Windows 也有熵池**，只是没有 `/dev/random` 这种文件形态：
`BCryptGenRandom` / `RtlGenRandom` 背后同样是系统 CSPRNG，硬件 RNG + 时序抖动供货。
所以"除了 Windows 都有"不成立——真正缺的是**玄铁这一层没做封装**，不是平台没有。

### 不可预测 ≠ 不能复盘

两条要同时满足：事前不可预测、事后可查。做法是"**判定即落档**"：

- 事件触发的那一刻取熵、算出结果，然后把这个结果（连同当时的种子/序号）写进存档与日志。
- 读档回来按存档里的结果走，不会重抽；玩家想刷也刷不动，开发者拿到日志却能复盘。
- 若允许"读档重抽"，那是设计选择（Roguelike 常见），要在文档里写明，别让它变成隐藏漏洞。

## 5. 伪随机的谱系：创作者该选哪一种

"真随机还是伪随机"不是二选一，而是一张**谱**。区别只有一个：**什么在推动随机流前进**。
推动源不同，玩家可干预程度、可复现程度、适合的玩法都不同。创作者要选的不是算法，
是"这条随机挂在什么上面"。

| 源 | 推进入什么 | 玩家能干预吗 | 读档能刷吗 | 适合 |
|---|---|---|---|---|
| **真随机（系统熵）** | 不推进，每次现取 | 不能 | 不能（同一档也重抽不到） | 遭遇判定、突脸、掉落、开关乱按时的鬼 |
| **固定种子 + 计数器** | 事件序号 | 不能 | 不能（序号在存档里） | 可分享种子的玩法、每日挑战、速通复现 |
| **按格步进** | 玩家走过的格数 | 能（多走两步就变） | 能 | 老 RPG 手感、速通"路线微调换命" |
| **按输入事件** | 每次按键 | 能（狂按就变） | 能 | 明确标为"可干预"的彩蛋玩法 |
| **时间戳（秒）** | 现实时间 | 半能（卡秒） | 同一秒内不能 | 按时段变化的内容（白天/夜里事件） |
| **时间戳（毫秒）** | 现实时间 | 几乎不能 | 不能 | 想"每次都不一样"又不想读熵时的廉价替代 |
| **位置/进度哈希** | 玩家的格 + 进度 | 不能 | 不能 | 门后房间内容、同一格子永远同一结果 |

几个容易说错的地方：

- **"玩家怎么走"本身不会改随机**——除非引擎把随机流挂在步数或输入上（上表第 3、4 行）。
  挂在事件点上取熵，上右上和上右左右上得到的结果没有区别，玩家也就没有"仪式"可做。
- **秒还是毫秒**：秒级只够做"按时段变"，同一秒内读档结果相同，玩家能卡；毫秒级几乎不可控，
  但跨机器、跨时区的一致性差（也容易被"改系统时间"钻空子）。要做每日内容就用**日期**，
  不要用秒。
- **读档重抽是设计选择，不是缺陷**：`位置哈希` 和 `固定种子+计数器` 天然防刷；
  真随机反而允许重抽（每次取熵都不同）。要防刷就用前两种，要"每次都新鲜"就用真随机。
- **位置哈希的隐藏价值**：它顺手修掉了老 RPG 里"同一个门，读档后进去是另一个房间 /
  剧情错乱（主角变精灵、立绘变配角）"那类 bug——内容由格子决定，不由内存里的随机状态决定。

### 给创作者的配置形态（写进 `剧情/幕NN.json`）

创作者只写"这条随机挂在哪、要多不可控"，不写算法：

```json
"随机": {
  "遭遇": { "源": "真随机", "概率": 0.3, "结果": "鬼_突脸" },
  "房间内容": { "源": "位置哈希", "表": ["实验室", "储藏间", "空房"] },
  "每日彩蛋": { "源": "日期", "表": ["旧报纸", "断线电话", "湿脚印"] }
}
```

引擎侧规则：**判定点固定 → 取源 → 结果与所用源一起落档**。这样创作者不用懂随机数，
玩家不用做仪式动作，开发者还能复盘。

### 默认口径（本作）

- 危险判定（遭遇、突脸、死亡）默认 **真随机**；
- 房间/门后内容默认 **位置哈希**（同一格永远同一结果，防剧情错乱）；
- 每日/按时段内容默认 **日期**；
- 按格/按输入的伪随机只作为**可选玩法**（老派手感、速通挑战），默认不开。

## 6. 熵兜底：混合源伪随机（没有熵接口时的回退）

> 定位：**这是回退，不是替代。** 系统熵拿得到就直接用；拿不到（旧系统、受限运行环境、
> 语言层没封装）才走这套。它做的事，本质上就是操作系统熵池自己在做的事：
> 把各种"抖动"搅在一起当不可预测输入。

### 6.1 混合的正确做法

候选抖动源：高精度单调时钟（微秒级差值）、帧序号与帧率、按键/鼠标**事件间隔**、
鼠标坐标与窗口位置、进程启动时长、内存/磁盘/网络计数、CPU 负载。

**关键：不要相加。** 加法可逆、可预测，几个粗糙量加起来熵不会变多。

正确链条是：拼成字符串 → 多轮搅动（异或 + 乘加 + 位移，或直接哈希）→ 取 32/64 位 →
与引擎自己的随机流混合。搅动函数只要"输入差 1 位、输出差一半位"就够了，不需要密码学强度。

同时把 **最终值 + 用了哪些源 + 每源原始读数** 写进日志（不写进玩家可见界面），
因为这套方案换掉了可复现性，出问题只能靠日志复盘。

### 6.2 各项的质量与代价（别指望 CPU 占用率能救场）

| 源 | 熵质量 | 读取代价 | 权限/隐私 | 备注 |
|---|---|---|---|---|
| 高精度时钟差值 | 中 | 极低 | 无 | 最好的廉价源，微秒抖动天然存在 |
| 按键/鼠标事件间隔 | 中 | 无 | 隐私：只记时序，不记内容 | 人手抖动是真人味所在 |
| 鼠标坐标 / 窗口位置 | 中 | 极低 | 无 | 玩家一动就变 |
| 帧序号 / 帧率 | 低 | 极低 | 无 | 可被玩家观察、可被拖慢 |
| CPU 负载 | 低 | 中（要读系统统计） | **可能受限** | 粒度粗（0.1–1 秒取整），别每帧读 |
| 内存 / 磁盘 / 网络计数 | 低 | 中 | 部分平台受限 | 只作凑数 |
| 进程启动时长 | 极低 | 极低 | 无 | 一次就定，之后不再变 |

结论：真正管用的是**时钟微抖动 + 输入事件间隔 + 鼠标坐标**这三样；
CPU 占用率、内存计数是"有就加，没有也不心疼"的凑数项。

### 6.3 缺项怎么办（这就是你问的那件事）

- **启动时探一次，别每帧探**。探不到就记一条"源不可用"，运行时不重试（省 syscall，
  也避免每帧读 CPU 统计把帧率拖垮）。
- **缺项 = 跳过，不报错、不阻塞**。还剩 ≥1 项就继续算，只是**质量降级要写进日志**：
  `熵兜底：源=时钟+按键间隔，质量=中`。
- **一项都没有**（极端情况）：退到 `时.现()` + 帧序号，标记 `质量=低`。
  玩法照跑，只是结果变得可预测、可刷——这是回退的代价，不是故障。
- **权限被拒**同样按"缺项"处理：不弹窗、不重试、不要求授权，少一项接着算。
  **绝不能因为读不到 CPU 负载就让随机事件不触发**——那会把体验 bug 变成功能事故。
- **隐私**：只读本机、只在本机算、不联网、不上传、不落盘原始读数（日志里只留最终值）。

### 6.4 该公示什么

游戏开屏的"内容提示"或设置页加一句就够，不用长篇：

> 本作使用本机时间、按键时序等本机信息生成随机数，仅在本机计算，不联网、不上传。

注意措辞：写"**按键时序**"而不是"键盘输入内容"——我们只取间隔与时刻，不记录按了什么。

### 6.5 已知局限（写清楚，别当它等于真随机）

- 可复现性丢失：录像复盘、玩家反馈都只能靠日志里的最终值。
- 可被操纵：故意拖慢帧率、卡时间点，能影响结果。要防刷就别用它，用系统熵或位置哈希。
- 逃不过"读档重抽"：每次取都不同，读档自然也重抽。这是设计选择，写进文档。
- 不该当默认：默认永远是系统熵；这套只在"熵不可得"时启用。
