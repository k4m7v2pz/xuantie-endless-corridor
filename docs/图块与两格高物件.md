# 图块与两格高物件

RPG Maker 那套地图里，地砖是一格，柜子、书架、墙柱、门框是**两格高**。
这不是美术偏好，它同时在三个地方生效：数据怎么记、碰撞怎么判、绘制谁盖谁。
本文把这三条定下来，并写清玄铁版现在缺什么。

**现状前提**：`主函数.xt` 里的 32px `格宽` 只服务于逐格移动，场景仍是手绘矩形
（上下墙、地板、粉笔划痕、台阶、铁门都是 `绘矩形` 画出来的）。**没有图块层、没有物件层、
也没有地图数据**。所以这条要落进「图块系统」，不是改一个常量就能到位。

---

## 0. 为什么是两格：斜俯视的必然结果

RM 的镜头不是正俯视，也不是正侧面，而是**斜俯视**（约 45° 往下看，俗称 2.5D / 娃娃屋视角）。

- 竖直的物体，**正面照常是矩形**（因为它是竖的，正对着你）；
- 它的**顶面**被摊成一个平行四边形贴在上方；
- 于是"能认出来这是什么"所需的信息刚好是「正面 + 顶面」两截，而一截只有 1 格高，
  两截就要 2 格。柜子、书架、墙柱、门框全是这个原因，不是美术偷懒。

**屏幕上半部分的墙，正面和顶面都在画面内**（你在房间里往下看，那面墙在远处、它的正面朝着你）；
**屏幕下半部分的墙只剩一条棱**（那是被"剖开"的近侧墙——它背对你，正面朝向屏幕外，
只能看到墙顶那条边）。娃娃屋剖开一面才看得见里面的地板，同一个道理。

推论：**这套视角和「横向走廊」是两套相机**。当前 `主函数.xt` 是横向走廊（上下墙 + 一条通道），
墙是整面高墙、不需要顶面；一旦走 RM 式俯视地图，上下墙的坐标体系、走位、遮挡都要换。
两者共用格与移动，但别混着画。

素材许可顺带记一笔：RM 引擎**收费且闭源**（MV/MZ 的 runtime 脚本能在安装目录里看到，
但按 EULA 不能拿去做别的引擎或单独再分发）。它自带的 **RTP 素材只在用 RM 做的游戏里可用**，
不能抠出来喂给本项目——要 48 网格素材就自己画，或买/找有单独商用授权的素材包。
开源的那几个（EasyRPG Player 跑 2000/2003、mkxp 跑 XP/VX 系）是**兼容运行时**，
解决的是"游戏不开编辑器也能跑"，不等于 RM 免费。

## 1. 一格定多大：先定死，别混

| 方案 | 格边长 | 适合 |
|---|---|---|
| 沿用现值 | 32 | 自己画图块、界面像素风 |
| RM 标准 | 48 | 复用现成 RM / MV / MZ 图块素材 |

**结论按素材来源定**：要复用现成 RM 素材就 48（MV/MZ 全是 48，缩到 32 会糊，
32 的图放到 48 会缺边）。定了就写进常量，同时进地图 JSON（`"格": 48`），
移动速度、窗口可见格数都跟着这个数走。

两格高物件的图就是 `格 × 2格`：48 网格下是 **48×96**，Retina 出 `@2x` 即 96×192。

## 2. 三种"高"，别混成一个概念

| 类型 | 占格 | 画在哪 | 挡人 |
|---|---|---|---|
| 地面 / 地砖 | 1×1 | 最底 | 否 |
| 两格高物件（柜、墙柱、门框、书架） | 2×1（脚在下格） | 物件层 | 是 |
| 可穿装饰（血迹、水洼、地砖缝、★ 标记物） | 1×1 | 地面之上、角色之下 | 否 |

RM 的 ★ 星号就是第三条：能盖在地面上、玩家从上面走过去的小东西（草丛、地毯、污渍）。
它和"两格高物件"唯一的共同点是都在地图数据里，行为完全相反，别共用一套判定。

## 3. 碰撞只认脚格，但两格都要登记

正确的登记方式：两格高物件在占位集合里写**两个格**，脚在下格、上半格也标"不可走"。

- **只登记下格** → 玩家能走进柜子上半格，半个身子埋进柜子里，视觉上是穿模。
- **两格都登记** → 玩家站在柜子正下方那一格时，脚格不与柜子相交，可以贴到跟前；
  这时柜子的下半截会挡住玩家上半身（前提是第 4 条做了排序），正是 RM 里"站在柜子前"的样子。

通行性先只做"通 / 不通"二值。RM 的通行性是按四方向记的（能从左边进、不能从下边上），
那是给"半高台阶""单面墙"用的，等真的需要再补，别一开始就上四分方向。

## 4. 绘制顺序：按底边 y，不是"角色永远最后"

`docs/绘制层级与视觉覆盖.md` 里写的是"主角画在物件之后即可，正侧面走廊不需要 y 排序"——
那是正侧面走廊的结论。**一旦物件两格高、地图是俯视四方向，这条就不够了**：

- 玩家在柜子**下方**（y 更大）：玩家应该盖住柜子底部 → 玩家后画。
- 玩家在柜子**上方**（y 更小）：柜子应该盖住玩家 → 柜子后画。

算法很朴素：每帧把「物件 + 角色 + 怪物」收成一个列表，按**底边 y** 升序画，
同 y 时物件先、角色后（站在同一格上时角色盖住物件脚）。

优化（对象多才需要）：静态物件按行分桶，只对玩家所在行 ±2 行做局部排序，
其余整行整行地画。地图几百格时这是必须的，几十格时不必。

## 5. 地图数据放哪：和剧情一样，不进 `.xt`

地图是数据不是引擎。放 `剧情/地图NN.json`（或每幕内嵌一张），`.xt` 只读、只画：

```json
{
  "格": 48,
  "地面": [["石地", "石地"], ["石地", "水洼"]],
  "物件": [
    { "图": "柜子", "x": 3, "y": 6, "高": 2, "挡": true },
    { "图": "血迹", "x": 5, "y": 4, "高": 1, "挡": false }
  ]
}
```

`高` 是格数（1 或 2），`挡` 是碰撞开关。图块图片本身在 assets 仓 `tiles/`（含 `@2x`）。

## 6. 技术硬点：渲染库现在切不了图块集

图块系统的前提是"从一张大图里抠出某一格来画"。查 1.3.11 的实际导出，这块是缺的：

| 需要的能力 | 现状 |
|---|---|
| 按源矩形画纹理（raylib `DrawTexturePro` 的 src 参数） | **没有导出**。`绘纹理区` 是把**整张**纹理缩放贴进目标矩形，没有源区参数 |
| 纹理池大小 | **32**（句柄 1–32，满了返回 0） |
| 裁剪 | 有：`裁剪开始(x,y,宽,高)` / `裁剪结束()` |
| 缩放贴图 | 有：`绘纹理区` / `绘纹理区精` |

三条可行路线：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 单格一张 PNG | 构建时脚本把图块集切成一个个 `格×格` 文件，`绘纹理区` 贴格 | 纹理池 32 上限——一幕最多 32 种图块，换幕要释放重载 |
| **B 一张图块集 + 裁剪** | `裁剪开始(格位)` → `绘纹理区(表, 格x-列×格, 格y-行×格, 表宽, 表高)` → `裁剪结束` | 每格多两次 C 调用；整张大图每格重采样（GPU 上很便宜）。**Retina 正确**，池只占 1 个 |
| C 补上游 | 给渲染库加 `绘纹理源区(纹理, 源x,源y,源宽,源高, 目标x,y,宽,高, …)` | 要动上游。这是真正的正解，值得提 issue |

**起步用 B**：零切图、不占池、`@2x` 自动生效（`加载纹理` 会优先找 `图块集@2x.png`）。
C 写进上游建议稿，不作为当前依赖。

## 7. 落地切片（每片都能单独验证）

1. **地图数据 + 铺地面**：一格地面按 JSON 铺满通道，走动逻辑不动。
2. **一个两格高物件**：柜子占两格、两格都不可走、按底边 y 排序；
   验"走到柜子正下方能贴住、上半身被柜子挡住""从上面走近会被柜子挡住"。
3. **多物件 + 行桶排序**：摆一排柜子/柱子，验遮挡不闪、不错位。
4. **自动元件拼边**（A2 那种 2×3 模板，按邻接选边缘）：这块最费事，放后面。
5. 门 / 动画 / 可穿装饰层。

别一次做完 1–5。第 2 片就能把"两格高"的全部争议（碰撞、遮挡、数据格式）验掉，
它是这套系统的最小闭环。
