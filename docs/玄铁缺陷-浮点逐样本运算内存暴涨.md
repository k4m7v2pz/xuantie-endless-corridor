# 玄铁缺陷记录：浮点逐样本运算导致内存严格线性增长

> 状态：**已复现，未上报上游**。2026-11-21 初版由本项目撞到并记录，
> 同日经复核（同一台 M3 机器）校正了初版的两处错误，数据见下。
> 缺陷在 `1.0-rc.5` 与 `v1.0-rc.6-dev.4` **两个包上一致存在**。
> 如果以后有人问"玄铁有没有缺陷"，这条可以直接拿出来；也可以原样转达上游。

## 1. 一句话结论

**每轮浮点表达式分配的对象不回收**，进程常驻内存（RSS）随循环次数**严格线性上涨，约 709 字节/轮**。
时间并不算慢（百万轮约 1.1 秒），**先死的是内存**：千万级样本才会到 GB 量级，随后被系统 SIGKILL（exit 137），
全程没有任何提示，表现为"程序跑着跑着消失了"。

## 3. 最小复现（探针，可原样复用）

```text
设 个 = 0
设 累 = 0.0
当 个 < 432000 {
    设 时秒 = 个 * 1.0 / 48000
    设 值 = 数学.正弦(6.2831853 * 1200 * 时秒 + 2.5 * 数学.正弦(6.2831853 * 1200 * 1.41 * 时秒))
    设 衰 = 数学.幂(2.718281828, 0 - 时秒 * 1000 / 30)
    累 = 累 + 值 * 衰
    个 = 个 + 1
}
示(累)
```

**关键点：必须是真浮点。** `个 / 率` 这种写法在玄铁里是**整数除法**，
`个 / 48000` 恒为 `0`，循环退化成常量运算，复现不出来（见第 8 节）。

## 4. 实测数据

| 迭代数 | 耗时 | 内存峰值 RSS |
|---|---|---|
| 108,000 | 0.51 s | 78 MB |
| 216,000 | 0.58 s | 155 MB |
| 432,000 | 0.74 s | 307 MB |
| 1,000,000 | 1.13 s | 709 MB |

- 斜率 ≈ **709 字节/轮**，严格线性（迭代翻倍，RSS 也翻倍）。
- **隔离对照**：同样 432,000 次只做 `信.追加(0)`（不含浮点）→ 2.2 MB / 0.41 s。
  说明内存与字节流追加无关，全部来自浮点表达式。
- 换算：1,000 万样本 ≈ 7 GB —— 这才是会被系统杀掉、且不给任何提示的量级。

## 5. 原因（已被数据间接证实）

1. **浮点结果装箱**：`数学.正弦` / `数学.幂` 与浮点运算返回 `XTValue`（boxed），
   每次运算都在堆/Arena 上分配对象；
2. **Arena 不在循环内回收**：短生命周期对象进 Arena 后要等整个函数返回才释放，
   于是每轮都在累积。

两条合起来正好给出"709 字节/轮、与字节流无关、线性"这三个特征，因此可以作为已证实的解释。
（初版曾把 `字节.追加` 的方法派发列为疑点，隔离实验已排除。）

## 6. 当前规避（本项目做法）

**不要在玄铁里逐样本合成音频。** 音频/大规模数值计算放外部工具生成，玄铁只做 IO：

- `文字剧情/生成音效.py` 用 python 的 `math` + `wave` 生成 FM 音效 wav（90ms 用时约 0.01 秒）；
- 玄铁侧只用 `渲染.加载音效(文件)` + `播音效(句柄)`。

附带的正面结论：`设 信 = 字节(n)` + `信.追加(x)` + `文件.写(路径, 信)` 是**二进制安全的**
（实测 `1 / 2 / 255` 写出后原样为 `01 02 ff`），所以少量字节的 WAV 头拼接在玄铁里完全可行，
卡住的只有"逐样本的长数值循环"。

## 7. 建议给上游的修法（按收益排序）

1. **未逃逸的纯局部浮点编译成原生 `double`**：函数内变量不存进容器、不返回到外部时，不进 `XTValue`。
   这一条能一次性解决绝大多数"算数字"的循环，收益最大。
2. **Arena 支持每轮循环回滚**：让一轮迭代的中间对象在下一轮开始前被回收。
3. **数学函数返回原生 `double`** 而不是 `XTValue`。

## 8. 初版更正记录（重要）

初版（2026-11-21 提交 `fd6a4b6`）写的是"4320 个样本跑 2 分钟未出结果、被 SIGKILL(137)"，这条**是错的**：

- 初版复现代码用了 `设 时秒 = 个 / 率`，两边都是整数 → **整数除法恒为 0**，循环里根本没发生浮点运算；
- 按原样跑，4320 样本只需 **0.43 s / 4.9 MB**；
- 因此当时观察到的卡死不可能来自"4320 样本"，属误判（更可能是当时进程一直没退出、被外部超时机制强杀）。

本文档第 3、4 节已按复核数据全部改写。**要复现请用第 3 节的探针**，不要用初版那段。
