# 文字剧情播放器（终端 TUI）

用玄铁写的一个纯终端文字冒险播放器，是这套「剧情 = JSON、播放器 = 引擎」结构的试验田：
它不需要渲染库、不需要窗口，专门用来在终端里快速验证剧情分支、演出节奏和输入体验。
两套剧情放这里跑，播放器本身是同一份代码。

## 目录

```
文字剧情/
├── 恐哀/          # 据某部同人恐怖作品的公开视频改写，四幕（作对照用）
│   ├── 剧情/       # 剧情 JSON —— 不入库（含角色名，属 IP 衍生内容）
│   ├── 剧情播放器.xt
│   └── 运行.sh
└── 我还会回来/      # 原创四幕
    ├── 剧情/       # 同上，不入库
    ├── 剧情播放器.xt
    └── 运行.sh
```

`剧情/`、`play` 产物、`日志/`、`*.dSYM/` 都在 `.gitignore` 里 —— **入库的只有引擎代码，
剧情留本地**。换剧情不用改代码，改 JSON 即可；代码可公开，剧本不发。

## 跑

```bash
bash 文字剧情/我还会回来/运行.sh     # 源码新过产物会自动重编译
XTC=<xtc 路径> bash 文字剧情/恐哀/运行.sh
```

手动编译（在故事目录内，产物名必须是 `play`）：

```bash
$HOME/Library/Caches/xtl/core/darwin-arm64/xtc-package/xtc tie 剧情播放器.xt -sc play
```

## 剧情 JSON 结构

`剧情/目录.json`：

```json
{ "作品": "标题", "幕": ["剧情/幕01.json", "剧情/幕02.json"] }
```

幕文件：

```json
{ "幕编号": 1, "幕名": "…", "起始": "首个节点名", "事件": { "节点名": { …节点… } } }
```

节点字段（除 `标题/正文` 外都可省）：

| 字段 | 作用 |
|---|---|
| `标题` | 节点名，打在分隔行上 |
| `正文` | 字符串数组，逐行输出 |
| `红字` | 字符串数组，在正文之后用 ANSI 红色输出 |
| `谜题` | `{ 提示, 答案?, 可接受[], 对白, 对, 错白, 错, 变体? }` |
| `选项` | `[{ 文字, 到 }]`，选完跳 `到` |
| `后继` | 普通推进跳哪个节点；`null` 表示本幕结束 |
| `调查` | 场景调查清单，见下 |
| `声` | `{ 毫秒, 频率?, 延迟?, 选项? }`，进节点时合成音效（**不建窗口也能响**）。无 `选项` 走纯正弦；有 `选项` 透传合成器，见下 |
| `打字` | `真`（每字 140ms）或整数（每字毫秒）。正文逐字出现、每字一响，不写则整行一次输出 |
| `注` | 给人 / AI 看的解释，**播放器完全不输出**，见下节 |

`调查`：

```json
{ "出口": "默认去哪",
  "按件数": [ { "件数": 3, "到": "收集满去哪" } ],
  "对象": [ { "名": "树下的坑", "话": "一句话描述", "给": "一把松土" } ] }
```

玩家输数字看某个对象（`给` 不为 null 就收进行囊）、`b` 看行囊、`x` 或直接回车走。
走的时候按行囊件数匹配 `按件数`（高阈值优先），否则走 `出口`。
大多数对象只给一句话、什么都不给，这样"调查"才有意义。

`谜题` 允许多个正确答案，按"是不是同一个值"分两类处理：

**① 同一个值、只是写法不同 —— 不用列，播放器自动归一。**
比较前玩家输入和 `答案`/`可接受`/`变体.接受` 两边都会归一：全角数字转半角，
去掉空格（含全角空格）、冒号（`:``：`）、斜杠、横线、小数点、下划线，再去掉前导 0。
所以 `9:15:32`、`０９１５３２`、`9 15 32`、`91532` 都能命中同一个 `"答案": "091532"`。

**② 不同的值 —— 必须显式列出。** 12 小时制 `9:15:32` 与 24 小时制 `21:15:32`
是两个不同的值，**引擎不做换算**。

这是有意的：线索可以是任何东西——时间、编号、谐音、一句谜语的另一种读法——
引擎一旦内置"钟点换算"就得内置下一个领域规则，永远列不完。

换算发生在**写剧情的时候**，不在玩家输入的时候：写剧情的 AI（或人）先把玩家可能
怎么算想一遍——直接推理也行，调 bash / python 算一遍也行——算出来的结果**静态**
写进 `可接受` 或 `变体`。运行时引擎只做字符串比对，不思考、不调外部程序。
好处是换算错了能在写作阶段验算出来，而不是让玩家在锁前面猜。

- 只要都开锁、走同一段剧情 → 写进 `可接受`：

```json
"答案": "091532",
"可接受": ["211532"]
```

- 想让每个答案各带一句不同对白、甚至去不同节点（彩蛋，主线可再汇合）→ 用 `变体`：

```json
"变体": [ { "接受": ["211532"], "对白": "你按 21 点算的。也对。", "对": "开门" } ]
```

判定顺序：`答案` → `可接受` → `变体`，命中任一即算答对；命中变体就用变体的
`对白` 与 `对`，否则用谜题自身的。都不中才进 `错白`/`错`。
`变体` 的 `对` 可以指回主线节点，这样不同密码只差一句彩蛋，后面剧情完全一致。

## 失败与重试：惩罚判断，别惩罚路程

谜题和危险节点要遵守一条：**玩家为错误付出的代价，不能是重走已经走过的路。**

参照反例：某同人恐怖游戏把密码锁放在迷宫深处，打错直接死、没有存档提示也没有自动存档，
玩家只能再绕一遍长路回来重打。这样惩罚的不是"判断错了",而是"路线熟了"，
恐怖感被消耗成重复劳动。

本引擎的做法：

- 谜题错满 10 次自动走 `错` 指向的绕过节点，**不允许死局**（见上面判定顺序）。
- 想做"会死"的节点，把 `错` 指到"回到岔口前"的节点：代价是丢掉线索或物品、重答一次，
  而不是把玩家送回关卡开头。
- 真要长距离置死，必须先把玩家送回最近的可重试点（剧情里自己设回环节点），
  不要靠"重开一局"当惩罚。
- 调试与试玩可以启动时输入幕号直接从某一幕开跑，别把重试成本做成玩家的负担。

**引擎侧已经把存档做成了默认行为**：每过一个节点自动写一次 `日志/进度.txt`
（幕号、幕路径、节点、上一节点、行囊），下次启动时问一句"接着上次的 XX 走，
还是重开"。所以"忘了存档"这件事在本引擎里不存在——玩家不需要记住任何事，
作者也不需要为存档点设计 UI。

一句话：**难度来自信息，不来自工时。**

## `注`：写给人和 AI 的解释，玩家看不到

节点上可挂一个 `注` 对象，播放器**不读、不输出**，只给看剧情文件的人和写剧情的 AI 用：

```json
"注": {
  "意图": "错位台词",
  "说明": "这句不属于他，说出来就显得不对，喜羊羊在等他把后半句补上。",
  "真相": "台本是写给别人的，他念的是别人的台词"
}
```

- `说明`：这段为什么这样写（给作者、给主播解释，也防止 AI 下一轮改写时抹掉设计）。
- `真相`：玩家看不到的真实状态（比如"它其实不在这个房间里"），方便 AI 在后续节点保持一致。
- `意图`：一句话标签（`错位台词` / `场外凝视` / `循环收尾`），便于按类型检索。
- 其余键随便加，播放器一概忽略。

这是从 `rust-bevy-endless-corridor` 的 `metadata.ai_context` / `creator_hints`
搬过来的思路：剧情要能被机器读懂，也要能被"解释给人听"，但**解释本身不能进演出**。

## 声音怎么写

进节点响一次，字段形态：

```json
"声": { "毫秒": 260, "延迟": 500,
        "选项": { "波形": "白噪", "音量": 0.5,
                  "包络": { "起音": 0, "衰减": 40, "延持电平": 0.35, "释音": 200 },
                  "混响": { "房间大小": 0.7, "湿干比": 0.5 } } }
```

- 不写 `选项` → 纯正弦（`频率`+`毫秒` 的简单写法仍然有效）。
- 写 `选项` → 透传 `合成器`：波形（正弦/三角/锯齿/方波/白噪）、音量、`振荡器`（≤4 个，每项 `{波形,音量,频率比}`）、`音调`、`包络`（ADSR 毫秒）、`EQ`（三段落分贝）、`延迟`、`混响`、`扫频`。
- **带 `扫频` 时其余合成参数全部不参与**（走白噪过带通的专用分支）：呼啸/风声靠它，但加不了混响。
- `延迟` 是惊吓的时机：正文先出现，隔半秒再响。播放器会忙等这段时间，控制在 1 秒内。
- 经验值：短白噪 200~400ms 敲一下最有效；风/海浪这类底噪 4000~8000ms、音量压到 0.13~0.2。
- 合成器没有共振峰，做不出人嗓尖叫；它擅长"不是人的东西"——噪声、啸叫、低频压迫。
- 已定案的几块（按听感实测）：
  - **字幕/打字音（定案）**：白噪，70ms，包络 起音0 / 衰减10 / 延持0.12 / 释音55，EQ 中音+2 高音+3，间隔 140ms。
    听感是"一个字往外蹦"，先脆后缓落；80ms 间隔太快会糊成"下雨"，听不出一个字一个字。
    备选：同包络换成三角波，更硬但拖长，适合当设备/提示音；要更短就把 毫秒 压到 45、释音压到 20。
  - **变压器/设备通电**：100Hz 正弦为主 + 50Hz 垫底 + 一点 200Hz，无锯齿、无白噪，低音 +4、中音 -6、高音 -8，混响 0.8；加了锯齿会变成"电流炸响"，不像变压器。
  - **短促冲击**：白噪 200~260ms、音量 0.5、带混响，用来当"某一下"。
  - **unison（合成器没有这个键，手工拼）**：`振荡器` 三槽同波形、`频率比` 0.98 / 1.0 / 1.02，
    音量省略让它自动均分（总响度和单槽基本一致，不会变吵）。220Hz 时拍频约 4.4 次/秒，
    起伏明显。实听判断：**"像合成器插件拧了一下 unison"**（2026-11-21）。
    代价：三槽相位都从 0 起算，音头整齐偏硬；输出单声道，只有幅度拍频、没有左右分离；
    4 槽上限被 unison 吃掉 3 个。要更粗糙就把比例拉到 0.94 / 1.0 / 1.06（拍频约 13 次/秒）。

## FM 音效（生成音效.py）

渲染库的 `合成器` 是**加法叠加**（几路一起响），没有"谁调制谁"，做不出 FM 那种非谐音；
玄铁侧的音频接口又是"整段预渲染、没有流式回调"，采样循环只存在于库的 C 层。
所以 **FM 放在 python 生成 wav，玄铁只 `加载音效` 播**。

（更正一条早期写错的判断：曾说"几十毫秒的音频在玄铁里跑几分钟还把内存吃爆"——那是初版
整数除法假复现造成的误判，见 `docs/玄铁缺陷-浮点逐样本运算内存暴涨.md` 第 8 节。实测
90 毫秒（1984 样本）在玄铁里只需 1~2 ms、内存增量可忽略；浮点 709 字节/轮只让"长音频"
不划算，不代表短音不能做。真正把 FM 挡在外面的是上面那条"采样循环在 C 层"。）

另有一份 **C 版草案** `文字剧情/fm合成器.c`：两 OP 相位调制，可独立出 wav，也可按文件末尾
的三步接进渲染桥的合成器。**现在没有接库**——接进去要么改安装包（会被工具链更新覆盖），
要么把 TUI 切到 clang 手动链接，两条都还没做。

```bash
cc -O2 -o /tmp/fm 文字剧情/fm合成器.c -lm
/tmp/fm 22050 /tmp/滴.wav 1200 1.41 2.5 90 30 0.5 40     # 与 音效表.json 同参数
```

```bash
python3 文字剧情/生成音效.py 文字剧情/我还会回来/音效   # 按 音效表.json 生成
```

`文字剧情/音效表.json` 里一条 = 一个音，键名就是文件名：

```json
"滴": { "载波": 1200, "比": 1.41, "指数": 2.5, "毫秒": 90, "衰减": 30, "音量": 0.5, "淡出": 40 }
```

- **载波** 音高；**比** 调制÷载波（整数=和谐像乐器，非整数=非谐像金属）；**指数** 调制深度（0 干净，2~4 金属，6+ 糊成噪声）；
- **衰减** 指数衰减常数，**淡出** 末尾线性淡出（不给会在结尾硬切，听起来像"钟声突然断了"）。

剧情里引用：

```json
"声": { "文件": "音效/滴.wav" }
"声": { "序列": [ { "文件": "音效/滴.wav", "间隔": 0 }, { "文件": "音效/滴.wav", "间隔": 700 } ] }
```

`序列` 是"一个节点里排几条音"，间隔相对上一条；播放排在正文之后，正文读完时声音正好在滴。

## 校验

```bash
python3 文字剧情/校验剧情.py 文字剧情/我还会回来 文字剧情/恐哀
```

纯标准库，不依赖 jsonschema。查两件事：字段类型与必填（对照 `剧情.schema.json`），
以及**引用完整性**——起始、后继、选项的 `到`、谜题的 `对/错`、调查的 `出口/按件数·到`
指向的节点必须真的存在。写完剧情先跑这个，能挡掉"后继指到一个不存在的节点"这类问题。

## 写法约定（正文怎么写得"看得清"）

- **叙述（旁白）就是普通一句**：不带引号、不加「旁白：」之类前缀。终端里它和白字正文没区别，
  加前缀等于多一层 UI。
- **台词一律用「」括起来**，不写「某某：」这种冒号前缀。人物归属靠上下文和"他说/她问"交代，
  连续三句以上对话时补一句动作或"他说"锚定，避免读者数引号。
- **红字只承载一个重点**，一句话，别写成整段。红字是节拍器，不是第二段正文。
- **节拍优先于修辞**：一行一拍，长句拆短；场景切换、突转处留空行。玩家是扫读，
  每行信息超过一件就糊成灰块。
- **危险/谜题前必须有一句"看得见"的提示**：进入高风险节点之前的那一个节点里，
  用场景说话（桌上摊着张字条、有人叮嘱了一句、某样东西亮着/被摆得很显眼），
  让玩家自己感觉到"这里要先想清楚"。不要靠弹窗，也不要什么都不给。
- **线索必须先于挑战出现**：玩家在能动手之前就该已经看过提示。不要靠"锁和提示并排"指望
  他自己先去看提示——动线决定顺序，不是作者脑内的顺序。
- **关键物件不要横向并排**：黑暗、无高亮时并排等于没有先后，玩家只会撞上离动线最近的那个。
  要么沿动线依次出现，要么同一处成组（锁旁边就是提示），别让他先撞锁再读说明书。
- **存档/回环点靠近入口**：入口处就能存，别放在最深处——玩家最容易经过的地方才该是存档点。
- **可交互的东西必须显眼**：文本里要能被一眼扫到（给编号、给名字、重复出现），
  别把关键物件藏在长段描写中间——图块版则必须高亮/发光，黑暗中一摆等于没有。
- **描写感官事件，不写"你很害怕"**：写"它离得太近""你没有退，你也退不开"，
  让恐怖的因果自己成立，不要替玩家下判断。

## 已知坑（玄铁侧）

- `时.延时()` 能编译、运行才炸，等时用自建忙等循环。
- 字符串字面量不支持 `\xNN`，ANSI 转义要真 ESC 字节（源码里直接写或用脚本注入）。
- 行输入模式下 ESC 不能即时响应，所以"随时按 ESC 呼出行囊"做不到；要做只能接
  玄铁「字符流」的原始模式 + 事件循环，输入层得整套重写。
- 调查循环里空输入按"走"处理，否则输入断流时会原地空转刷屏。
- **音频不用建窗口**：`引 "渲染" 予 R` 只 `初始化音频()` 就能出声，`xtc tie` 直接成
  产物（2.1MB，自带 raylib），不必走 IR 截获那套。raylib 启动会往 stdout 打 6 行
  `INFO: AUDIO:`，用自己声明的 `外 函 SetTraceLogLevel(级别: 整)` + `SetTraceLogLevel(6)`
  静默掉。句柄池有限，换节点时记得 `释音效(上一句)`。
- `合成音效` 只有正弦波（`合成器` 才有波形/ADSR/混响），所以现在的"声音"是纯音；
  要做出刮擦、呼吸、尖叫这种质感得等 `合成器` 的参数接进来。
